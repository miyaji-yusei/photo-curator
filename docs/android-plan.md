## 0. 最初に — 前提の訂正

計画の出発点になっていた「PC 版は NAS のフォルダに選別結果も保存されるはず」は、
**実装を読むとそうなっていない。**

| 何が | どこに |
|---|---|
| SQLite（星・dHash・撮影時刻・連写の例外すべて） | `app_data_dir/photo-curator.sqlite3` |
| 256px サムネイル | `app_data_dir/thumbnails/` |
| 写真フォルダ | **一切書き込まない** |

根拠: `db_path()`（`src-tauri/src/lib.rs:260`）と `thumbnail_dir()`（同 `:275`）はどちらも
`app.path().app_data_dir()` 配下を返す。Windows では
`%APPDATA%\app.photocurator.desktop\`。写真フォルダへ書くのは
`export_by_rating` で出力先を明示したときだけで、既定では原本フォルダの外を要求する
（同 `:2609` で「出力先には、写真フォルダの外を指定してください」と弾いている）。

**したがって「Android から同じ NAS フォルダを読めば結果が共有される」状態は存在しない。**
共有したいなら新しい仕組みが要る。§6 の「サイドカー」がそれで、Routine 14 として計画する。

## 1. 今回決まっていること

| 論点 | 決定 |
|---|---|
| 写真の出所 | **端末ローカルを先に。** NAS(SMB) はその次 |
| SMB スパイクが失敗したら | **その時点で相談する。** 代替は分岐点として §11 に記録するだけ |
| オフライン運用 | **やらない。** NAS に繋がっているときだけ動けばよい |
| 選別結果の共有 | PC と Android で共有したい。都度読み書きは重いので端末側にキャッシュする。方式は任せる |
| NAS への反映 | NAS 上に「厳選」フォルダを作ってコピー。**原本は変更しない** |
| 対象 OS | Android 13 以上。実機あり・USB デバッグ可 |

## 2. 方式の比較と推奨

### 推奨: **A. Tauri v2 の Android ターゲット**

| 観点 | A. Tauri Android | B. Android Chrome でブラウザ版 | C. ネイティブ Kotlin で新規 |
|---|---|---|---|
| 既存資産の再利用 | **画面・選別ロジック・解析・DB をそのまま。** 再実装ゼロ | 画面と TS ロジックのみ。Rust コアは使えない | **ゼロ。** 全部作り直し |
| 実装量 | 中。Kotlin プラグイン（写真アクセス・SMB）と Rust の入口 refactor | 極小（ほぼ現状のまま） | 特大 |
| 性能 | Rust の解析がそのまま効く。EXIF サムネイル経路で 1.72ms/枚（Routine 1 実測） | Canvas + Worker。ブラウザの復号に依存 | Kotlin/JNI 次第。作り込めば最速 |
| OS 連携の自由度 | **高い。** Kotlin プラグインで MediaStore・SAF・SMB に到達できる | **ほぼ無い。** 写真ピッカー止まり。SMB もフォルダ走査も不可 | 最高 |
| 保守性 | 1 コードベースで Windows/iPad/Android。ただし Android 固有の層が増える | 最も楽 | **3 つ目の実装を永続的に抱える** |

### 推奨の理由

**捨てられる資産の量が決定的に違う。** 現時点で選別ロジックと解析は
Rust 53 件 / Vitest 191 件のテストを伴って存在する。中身は
トーナメント（`utils/tournament.ts`）、連写のまとまり編集（`utils/burstEdit.ts`）、
閾値学習（`utils/burstThreshold.ts`）、dHash（`utils/dhash.ts` と Rust 版）、
EXIF 解釈（`utils/exifReader.ts` と Rust 版）、キャッシュ無効化
（`fingerprint` + `d_hash_version` + `thumbnail_version`）。
**C はこれを全部書き直すことになり、テストも書き直しになる。**

**B は今回のゴールを満たせない。** ゴールは「NAS の写真を選別対象にする」だが、
ブラウザからは SMB に到達できず、フォルダ走査もできない。写真ピッカーで
1 枚ずつ選ぶ形しか取れない。

**A は既に踏み込める状態にある。** `src-tauri/Cargo.toml` の `crate-type` は
`["staticlib", "cdylib", "rlib"]` で、mobile が要求する形を満たしている。
`tauri android init` から始められる。

さらに、この判断はアーキテクチャの意図そのものと一致する。
`composables/photoBackend.ts` のコメントは「将来 PC のプロジェクトを遠隔選別する
`HttpBackend` を足すときも、このインターフェースを実装するだけで画面側は変えずに済む」
と明記している。**新しい実行環境はこのインターフェースの実装を増やす形で入れる**のが
設計の意図で、A はその線に乗る。

## 3. `PhotoBackend` をどう拡張するか

### 結論: **インターフェースはほぼ変えない。`TauriBackend` を Android でも共用する。**

Android でも Tauri ランタイムは存在するので `invoke` はそのまま通る。写真ソースの
違い（ローカルフォルダ / MediaStore / SMB）は **Rust 側で吸収**し、フロントには
今までどおり `Photo` を返す。新しいバックエンド実装は作らない。

理由は 2 つ。`TauriBackend` は実質すべてのメソッドが `invoke` の薄い委譲で、
Android 用に複製すると同じコードが 2 本になる。そして違いは「写真をどこから読むか」
だけで、そこは Rust の内部にある。

### ただし 1 か所、既に壊れている

```ts
// composables/backends/tauri.ts:30
isDesktop: isTauriRuntime,
```

`isDesktop()` が「Tauri か」と同義になっている。**Android では Tauri なので true を返し**、
実際には成立しない前提が次の場所で発動する。

| 場所 | 起きること |
|---|---|
| `app.vue:68` `groupSizeLimits(desktop.isDesktop())` | 1 グループ 10 枚（デスクトップ既定）になる。タッチ端末は既定 4 枚・上限 9 枚のはず |
| `app.vue:71` `isTouchOnly` | キーボードショートカットの案内が出る。Android には物理キーボードが無い |
| プロジェクト作成ダイアログ（`app.vue:2068` 付近） | `canImportPhotos`（= `importPhotos` の有無）で分岐しているのでこちらは無事だが、Android ではデスクトップ用のフォルダ選択欄が出る |

→ **能力を明示する形に置き換える**（Routine 9）。

```ts
export interface BackendCapabilities {
  /** フォルダを指定して走査できる（デスクトップ／Android の SAF ツリー・SMB）。 */
  browseFolders: boolean
  /** 物理キーボードを想定してよい。 */
  keyboard: boolean
  /** 原本のフルサイズを表示できる。 */
  fullResolution: boolean
  /** 星ごとのフォルダへ書き出せる。 */
  exportFolders: boolean
  /** 原本の XMP に星を書ける。 */
  writeMetadata: boolean
}
```

`isDesktop()` は意味を「PC のデスクトップか」に狭めて残すか、削除して `capabilities` に
一本化する。既存 2 実装への影響は `capabilities` を 1 つ足すだけで、呼び出し側は
`app.vue` の 3 か所を書き換える。**インターフェースのメソッドは増減しない。**

### 増えるコマンド（Rust 側）

写真ソースの選択と、サイドカーのために増える。フロントから見ると
`chooseFolder` / `createProject` の中身が変わるだけで、シグネチャは同じ。

| 追加 | 用途 |
|---|---|
| `list_photo_sources` | この端末で選べる写真の出所（端末フォルダ / SMB 共有）を返す |
| `connect_smb` / `disconnect_smb` | 接続とその生存確認 |
| `read_sidecar` / `write_sidecar` | §6 |

## 4. 写真ソースの取得経路

### 齟齬の正体

Rust の解析は **`&Path` 前提**で書かれている。

```
read_capture_time(path)     src/lib.rs:852
exif_capture_time(path)     :879
exif_orientation(path)      :1056
exif_thumbnail_image(path)  :1097
scaled_jpeg_decode(path)    :1134
decode_hash_source(path)    :1171
analyse_photo(.., source: &Path, ..)  :1294
fingerprint(path)           （fs::metadata）
run_scan → WalkDir::new(folder)       :1579
hash_one → Path::new(&record.path)    :1712
```

Android では `content://…` であって `Path` ではない。SMB ではリモートパスで、
`fs::metadata` も `File::open` も通らない。

### 解き方: **入口をバイト列にする**（Routine 10）

上のうち**実際に必要なのは「バイト列」と「fingerprint」だけ**である。
`exif_thumbnail_image` は APP1 セグメントしか読まないし、`scaled_jpeg_decode` は
`Read + Seek` があれば足りる。`image::open` は `load_from_memory` に置き換わる。

```rust
/// 写真の実体をどこから取るか。**解析コードはこれ以外を知らない。**
trait PhotoSource {
    /// 先頭 n バイト。EXIF サムネイル経路はこれだけで完結する。
    fn head(&self, id: &PhotoRef, bytes: usize) -> Result<Vec<u8>, String>;
    /// 全体。EXIF サムネイルが無い写真だけがここへ落ちる。
    fn all(&self, id: &PhotoRef) -> Result<Vec<u8>, String>;
    /// mtime と size。既存のキャッシュ無効化がそのまま効く。
    fn fingerprint(&self, id: &PhotoRef) -> Option<(i64, i64)>;
    /// 走査。
    fn list(&self, root: &PhotoRef) -> Result<Vec<PhotoRef>, String>;
}

/// 写真の指し先。DB の `photos.path` 列にそのまま入る文字列表現を持つ。
enum PhotoRef {
    Local(PathBuf),   // 既存のデスクトップ
    Content(String),  // content://…（Android の MediaStore / SAF）
    Smb { share: String, path: String },
}
```

**DB スキーマは変えない。** `photos.path` は既に `TEXT` で、`content://…` も
`smb://…` もそのまま入る。`PhotoRef` は文字列の前置きで判別する
（`content://` / `smb://` / それ以外はローカルパス）。既存行はすべてローカルパスとして
解釈されるので、**移行処理は不要**。

この refactor はデスクトップの挙動を一切変えない。**既存の Rust 53 件が
そのまま回帰テストになる**（特に `picks_the_cheapest_decode_path_that_works`、
`reuses_the_cached_thumbnail_until_the_photo_changes`、
`the_thumbnail_source_comes_back_upright`）。

### 端末ローカル写真（Routine 11）

Kotlin プラグインで MediaStore / SAF を橋渡しする。

- 権限: `READ_MEDIA_IMAGES`（Android 13+）。Android 14 の部分許可
  `READ_MEDIA_VISUAL_USER_SELECTED` も受け付ける
- 走査: SAF の `OpenDocumentTree` でフォルダを 1 回選ばせ、`takePersistableUriPermission`
  で URI 権限を永続化する。以後は再起動しても同じフォルダを走査できる。
  **これが `chooseFolder()` の Android 版になる**
- 読み出し: `ContentResolver.openInputStream(uri)` から `head` / `all`
- fingerprint: `DocumentsContract.Document.COLUMN_LAST_MODIFIED` と `COLUMN_SIZE`
- 表示: `convertFileSrc` は `content://` を扱えない。ただし**サムネイルは既に
  `app_data_dir/thumbnails/` にローカルファイルとして書いている**ので、
  一覧と選別画面はこの既存経路がそのまま使える

### NAS（Routine 12–13）

Kotlin プラグイン + smbj。`PhotoSource` の `Smb` 実装として入る。詳細は §5。

## 5. SMB の具体案とスパイク

### 案

Tauri v2 の Android プラグインを Kotlin で書き、**smbj**（SMB2/3、Apache 2.0、純 Java）を
使う。Rust からはコマンド 4 本だけを叩く。

```
smb_connect(host, share, user, password) -> sessionId
smb_list(sessionId, path)                -> [{name, size, mtime, isDir}]
smb_read(sessionId, path, offset, len)   -> ByteArray   ← 部分読みが要点
smb_close(sessionId)
```

`smb_read` に offset/len があることが性能上の急所。§7 を参照。

### その前に — 5 分で終わる確認（SMB を書かずに済む可能性）

**利用者は既に WebAccess A（Buffalo の Android アプリ）で NAS にアクセスできている。**
Android のベンダー製 NAS アプリは、**DocumentsProvider として自分を登録している**ことが
あり、その場合は他のアプリの SAF（フォルダ選択）にそのまま「出所」として現れる。

もしそうなら、**smbj も SMB の実装も要らない。** R11 で作る SAF 経路がそのまま
NAS に届く。R13 が丸ごと消える。

確認方法（実機で 5 分）:

1. 任意のアプリでフォルダ/ファイル選択を開く（Android の「ファイル」アプリでもよい）
2. 左のドロワー、または「⋮ → 内部ストレージを表示」で**出所の一覧**を出す
3. **WebAccess A（または Buffalo 系の名前）が並んでいるか**を見る
4. 並んでいたら、そこから NAS の写真フォルダまで辿れるかを確認する

**要検証であって、そうなっている保証は無い。** ただし当たれば実装量が大きく減るので、
R12 より先に、必ずこれを見ること。

なお当たった場合も性能は別問題で、DocumentsProvider が
**部分読み（`openInputStream` の途中で止める）に対応しているか**は測る必要がある。
対応していなければ 1 枚 6.7MB が流れる（§7）。

### スパイク（Routine 12・時間箱で区切る）

**実装前に、最小のコードで「できる／できない」だけを確かめる。**
本体のコードには一切手を入れず、捨てる前提で書く。

1. `pnpm tauri android init` が通り、素の Tauri アプリが実機で起動する
   （Routine 8 で済んでいる前提）
2. Gradle に smbj を追加し、**依存が解決してビルドが通るか**
   （ここで落ちるなら jcifs-ng を試す）
3. Kotlin で `smb_connect` と `smb_list` だけを実装し、JS から `invoke` して
   **NAS の共有フォルダのファイル一覧が返るか**
4. `smb_read(offset=0, len=65536)` で JPEG の先頭 64KB を取り、
   **その 64KB から EXIF サムネイルを取り出せるか**を Rust 側で確認する
   （実データでは APP1 が先頭 26KB で終わることを実測済み。§7）
5. 1 枚あたりの所要時間を測り、100 枚ぶんを外挿する

**打ち切り条件**: 2 か 3 で詰まったら深追いせず、失敗の内容（Gradle か、
SMB のバージョンか、認証か、Tauri のプラグイン機構か）を記録して相談する。

### NAS 側で実機確認が要ること

- SMB のバージョン（LS710D の管理画面）。**SMB1 のみなら smbj では繋がらない**
- 認証方式（ゲスト許可 / ユーザー認証）と、選別に使う共有名
- 日本語ファイル名のエンコーディングと、大文字小文字の扱い

## 6. 選別結果の共有 — サイドカー（Routine 14）

### 何を解くか

**PC と Android が同じ NAS フォルダを見ても、いま結果は共有されない**（§0）。
共有したいが、都度 NAS へ読み書きするのは重い。

### 方式

写真フォルダ直下に `.photo-curator/` を作り、**可搬な形**で結果を置く。

```
<NAS の写真フォルダ>/
  .photo-curator/
    catalog.json       星・撮影時刻・dHash・fingerprint・連写のペア例外
    thumbs/<id>.jpg    256px  一覧用（1 枚 6.6KB 実測）
    display/<id>.jpg   選別画面用（既定 1024px = 87KB 実測 / 設定で 1536px = 163KB）
```

2,000 枚で **thumbs 13MB + display 170MB ＝ 約 185MB**（1536 なら約 330MB）。NAS 側では問題にならない大きさ。

**`display/` を置くことが Android 実現の鍵。** これが無いと、選別画面が原本を
取りに行って 1 ラウンド 13.4GB になる（§7）。逆にこれがあれば、Android は
**原本を 1 バイトも読まずに選別を完走できる。**

なお `display/` を作るには原本を全部読む必要がある（EXIF 埋め込みサムネイルは
160px 程度で流用できない）。2,000 枚で 13.4GB。**これは一度きりで、PC 側でやれば
有線ギガビットで数分**。Android 単独でも可能だが Wi-Fi で時間がかかるので、
**PC で先に解析しておく運用を推奨**する。

**SQLite ファイルを NAS に置いて直接開くことはしない。** ネットワークファイルシステム上の
SQLite はロックが信用できず、2 端末が同時に開くと壊れうる。代わりに
**JSON を丸ごと読み、丸ごと書く**。1,000 枚でも数百 KB で、書き込みは選別の区切りだけ。

### 動き方（「端末キャッシュで工夫する」の中身）

1. プロジェクトを開いたとき `.photo-curator/catalog.json` を **1 回だけ**読む
2. 端末のローカル SQLite（既存の `app_data_dir`）へ取り込む。
   **以後の読み書きは全部ローカル。選別中に NAS へ触りにいかない**
3. サムネイルは `thumbs/` にあるものをローカルへコピーして使う。
   **これが最大の効き目**で、PC で解析済みなら Android は原本を 1 枚も落とさずに
   選別を始められる（§7）
4. 選別の区切り（ラウンド終了・アプリを閉じる・明示のボタン）で `catalog.json` を書き戻す

### 競合

同時編集は今回**想定しない**（1 人で使うため）。ただし黙って壊さないよう、
`catalog.json` に `updatedAt` と端末名を持ち、**読み込み時より新しくなっていたら
上書きせずに警告を出す**。書き込みは一時ファイルへ書いてから rename する
（`write_ratings_to_files` が `src/lib.rs:2799` 付近で既に同じ手を使っている）。

### 副次的な効果

デスクトップ版にサイドカーを入れると、**Android を待たずに単体で価値が出る**
（PC を入れ替えても結果が NAS 側に残る）。そのため Routine 14 はデスクトップ側だけ
先に入れてよく、**SMB の可否に依存しない**。

## 7. 解析の実行場所と性能

### 既にあるキャッシュ機構（確認済み・そのまま活かす）

一度解析した写真を再解析しない仕組みは**既に完成している。新しく作る必要はない。**

| 仕組み | 何を見るか |
|---|---|
| `fingerprint` | 原本の mtime + size。変わっていなければ再解析しない |
| `d_hash_version`（現在 2） | ハッシュ方式が変わったら、**サムネイルから引き直す**（原本には戻らない） |
| `thumbnail_version`（現在 1） | サムネイルの作り方が変わったら原本から作り直す |
| `get_analysis_backlog`（`src/lib.rs:2054` 付近） | 残作業が 0 なら事前生成すら起動しない |

**SMB でも `fingerprint` さえ取れれば（smbj で mtime/size は取れる）この全部がそのまま効く。**

### なぜ PC では気にせずに済んでいたのか（重要）

**PC も NAS からバイトを転送している。「その場で読む」ような仕組みは無い。**
ただし**全部は転送していない。**

Windows が NAS を `L:` としてマウントしているので、アプリは `File::open` して
順番に読み、Exif が見つかった時点で読むのをやめる。**Windows の SMB クライアントが、
実際に読まれた範囲だけをネットワークから取ってくる。**
つまり部分読みは**タダで手に入っていた**。そのためのコードは 1 行も書かれていない。

**Android にはアプリから使える OS レベルの SMB マウントが無い。**
アプリが自分で SMB を話すことになり、**このタダの部分読みが消える。**
素直に「ファイルを端末に落としてから既存のコードにパスを渡す」と書くと、
26KB で済んでいたものが 6.7MB になる。

なお、**原本を端末に置く必要は無い。PC でも置いていない。**
どちらもバイトをメモリに読んで解析し、捨てる。端末に残るのは 256px のサムネイル
（1 枚 約 20KB）だけで、これは PC でも同じ（`app_data_dir/thumbnails/`）。

### 転送量（実測にもとづく）

実データ（`L:\Pharfaite Showcase4`）で計測した。

- 1 枚あたり **6.5〜6.8 MB**（6000×4000）
- **Exif APP1 セグメントは先頭 26KB（ファイルの 0.38%）で終わる。**
  埋め込みサムネイルもその中にある。`exif_thumbnail_image` はここまでで用が済む
- 経路の内訳（271 枚、Routine 2 の実測）:
  `exif_thumbnail 264 (97.4%) / jpeg_scaled 7 (2.6%) / full_decode 0`

| 読み方 | 1,000 枚の転送量 |
|---|---:|
| **PC と同じ読み方**（26KB × 974 ＋ 全体 × 26） | **約 200 MB** |
| 素直に全ファイルを落とす | **約 6.7 GB** |
| サイドカーの `thumbs/` を再利用（PC で解析済み） | **約 20 MB** |

**200MB の内訳に注意。** 97.4% の写真は合計 25MB しかなく、
**残り 174MB は 2.6% の「Exif サムネイルを持たない写真」が全部読まれるぶん。**
ここは避けようがない（サムネイルを作るには画像本体が要る）。
つまり部分読みを実装しても、**削れるのは 6.7GB → 200MB まで**で、その先は
サイドカーでしか縮まない。

Routine 1 の実測では EXIF サムネイル経路のデコードが **1.72 ms/枚**（ローカル）で、
SMB では I/O が支配的になる。

### 最大の問題 — 選別画面が原本を表示している

`app.vue` の `img :src` を全部洗った結果、**解析より選別中の表示のほうが重い。**

| 画面 | 表示元 |
|---|---|
| 選別画面（`app.vue:1844`） | **原本（6.7MB）** |
| 連写の見直し（`:1998`）・連写ダイアログ（`:2322`） | **原本** |
| 閾値学習の比較（`:1717`）・拡大表示（`:2115`） | **原本** |
| プロジェクト詳細・結果一覧・移動ダイアログ | 256px サムネイル |

PC では NAS がマウントされていて OS がキャッシュするので表面化しないが、
**Android では選別 1 ラウンドで 2,000 × 6.7MB = 13.4 GB が流れる。**
解析パス（200MB）の 67 倍で、**ここが実現性の急所。**

### なぜそうなっているのか（実測で判明）

保存されているサムネイルは **実際には 160×120**。`scale_for_thumbnail` は
長辺が 256px 以下なら拡大しない（「引き伸ばしても情報は増えない」）ため、
**EXIF 埋め込みサムネイルがそのまま保存されている。** 実測 6.6KB の小ささもこれで説明がつく。

実データで確認した JPEG の中身（`2026-04-29_17-17-20_460.jpeg`、6.71MB）:

```
@      2  APP1   len=27392  Exif   ← この中に 160x120 の埋め込みサムネイル（約14KB）
@  27396  APP1   len= 2560  XMP
@  29958  DQT / SOF0 / DHT
@  30531  SOS                      ← ここから先が画像本体（6.68MB）
埋め込み JPEG は 1 つだけ（offset 12784）= 上記の 160x120
```

**大きなプレビュー画像は埋まっていない。** つまり表示用サイズを得るには原本の全読みが要る。

160×120 では写真の良し悪しを判断できないので、選別画面は原本を出すしかなかった。
**「160×120」と「原本」の間が空いている**のが構造的な欠落で、R10b がそこを埋める。

### 解く: 表示用サイズ（1536px）を導出する

解析のときに 256px のサムネイルに加えて **長辺 1536px の表示用画像**（実測 163KB）も作り、
上の「原本」と書かれた画面をすべてそちらに向ける。
原本は**拡大表示を押したときだけ**、その 1 枚を取りに行って捨てる。

### サイズの根拠（Galaxy Z Fold 8 実機で計測）

`SM_F971C` を USB で繋ぎ、実写真を実機の画面に並べて測った。**推測ではない。**

- メイン画面（開いた状態）: 2448×1848 / density 420 → **CSS 933×704 / DPR 2.625**
- カバー画面: 1248×1972 / density 420 → **CSS 476×752 / DPR 2.625**

**画像が最大になるのは 1 グループ 2 枚のとき**（利用者の使い方）。縦写真 2 枚を
横に並べ、UI が占める高さの割合を変えて測った結果:

| 状態 | 写真 1 枚（実画素） | 必要な長辺 |
|---|---|---:|
| カバー画面（**比率によらず一定**） | 578×868 | **868px** |
| 開いた状態・写真域 70% | 825×1238 | **1238px** |
| 開いた状態・写真域 75% | 887×1330 | **1330px** |
| 開いた状態・写真域 80% | 約 940×1420 | **1420px** |
| 開いた状態・写真域 100%（UI なし） | 1179×1768 | 1768px |

カバー画面は**横幅で頭打ち**になる（写真の上下に余白が出る）ので、UI の作り方に
左右されず 868px で一定。**要件を決めるのは開いた状態。**

利用者の見立てでは UI 込みで写真域は 70〜80% になる見込み → **1238〜1420px**。

### 候補の比較（符号化は品質 82、実写真で計測）

| 長辺 | 1 枚 | 2,000 枚 | 70%(1238) | 75%(1330) | 80%(1420) | カバー(868) |
|---|---:|---:|:-:|:-:|:-:|:-:|
| 512 | 30 KB | 59 MB | ✗ | ✗ | ✗ | ✗ |
| 768 | 55 KB | 107 MB | ✗ | ✗ | ✗ | ✗ |
| 1024 | 87 KB | 170 MB | ✗ | ✗ | ✗ | ○ |
| 1280 | 123 KB | 240 MB | ○ | ✗ | ✗ | ◎ |
| **1536** | **163 KB** | **318 MB** | ◎ | ◎ | ◎ | ◎ |
| 1920 | 約 250 KB | 約 490 MB | 過剰 | 過剰 | 過剰 | 過剰 |

### 決定: 固定値ではなく**利用者が選ぶ設定**にする

実機で確かめた結果、利用者の実際の使い方は **1 グループ 3〜4 枚が中心、多いときは 10 枚**で、
2 枚は「じっくり見比べたいとき」に限られる。3〜4 枚なら必要な長辺は **733px**、
9 枚なら **489px** なので、**普段は 1024 で十分**。

そこで固定値をやめ、**解析を始めるときのトグル**にする。

| UI | 値 |
|---|---|
| **「大きな画像で選別する」OFF（既定）** | **1024px**（87KB/枚・2,000 枚で 170MB） |
| **ON** | **1536px**（163KB/枚・2,000 枚で 318MB） |
| 高度な設定 | 768 / 1024 / 1280 / 1536 / 1920 から選べる |

参考（実測、品質 82）:

| 長辺 | 1 枚 | 2,000 枚 |
|---|---:|---:|
| 768 | 55 KB | 107 MB |
| **1024** | **87 KB** | **170 MB** |
| 1280 | 121 KB | 236 MB |
| **1536** | **163 KB** | **318 MB** |
| 1920 | 238 KB | 465 MB |
| 2048 | 267 KB | 521 MB |

### 設定を変えたときの作り直し（素直に作ると壊れる）

**選んだ長辺を DB に持たないと、設定を変えても古い画像が使われ続ける。**
`thumbnail_version` と同じ轍。`photos` に `display_edge`（実際に生成した長辺）を持たせ、
要求値と突き合わせる。

そのうえで**上げるときと下げるときで扱いが違う**ことに注意する。

| 操作 | 必要なこと | 代償 |
|---|---|---|
| 1024 → 1536（**上げる**） | **原本を読み直す。** 1024 の画像から 1536 は作れない | 2,000 枚で 13.4GB の再転送 |
| 1536 → 1024（**下げる**） | **保存済みの 1536 を縮めるだけ。** 原本に戻る必要はない | ほぼゼロ |

→ **下げるときは原本を読まない**経路を用意する。`d_hash_version` が「サムネイルから
引き直す」経路を持っているのと同じ考え方で、既存の設計に素直に乗る。

上げるときは重いので、**トグルを変えると何が起きるかを UI で明示**し、
解析を始める前に決めてもらう。

### いつ作るか — **最初の走査では作らない**（重要）

表示用画像を作るには原本を全部読む必要があるので、**これを初回走査に混ぜると
デスクトップの解析が桁で遅くなる。** Routine 1 の実測では
EXIF サムネイル経路 **1.72ms/枚**、フルデコード **132ms/枚** で **77 倍**。
2,000 枚なら 3.4 秒が 4.4 分になる。

→ **2 段階に分ける。既存の仕組みにそのまま乗る。**

| 段階 | 何をするか | 原本の読み方 |
|---|---|---|
| **走査（`run_scan`）** | 撮影日時・dHash・256px サムネイル | 先頭 26KB（97.4%） |
| **事前生成（`startBackgroundAnalysis`）** | 表示用画像 | 全体 |

`startBackgroundAnalysis` は **scan 完了後に UI をブロックせず走る仕組みとして既にある**
（`PhotoBackend` にも `getAnalysisBacklog` とセットで定義済み）。ここに表示用の生成を
足すだけでよく、新しい仕掛けは要らない。

こうすると:

- **走査が終わった時点で連写のまとめと閾値学習は始められる**（dHash が揃っているため）
- 表示用は裏で溜まっていく。まだ無い写真は**その場で作る**（選別中のグループぶんだけ、
  次のグループを先読みしておく）
- Android では、まだ無い写真だけが原本を取りに行く。**サイドカーに揃っていれば 0**

`get_analysis_backlog` の条件に `display_edge` の不足を足せば、
「事前生成すべき残り」の数え方も既存のまま使える。

**この変更は Android 専用ではない。** デスクトップでも選別画面が毎回 6.7MB を
デコードしなくなるので、そちらでも速くなる。

### 効くのは総量ではなく「回数」

表示用を作るには原本の全読みが要るので、**総バイト数だけ見ると変わらないように見える。**
違うのは回数。

| | 原本の全読みが起きるとき | 2,000 枚での総量 |
|---|---|---|
| いま | **選別画面で見るたび。** ラウンドを重ねるたび再取得 | 13.4 GB **× ラウンド数** |
| R10b 後 | **表示用を作る 1 回だけ。** 以降どのラウンドでも読まない | 13.4 GB **× 1**（PC で済ませれば Android は 0） |

トーナメントは何ラウンドも回すので、いまのままだと選別するほど積み上がる。

### 原本を読む場面は、R10b 後は 3 つだけ

| 場面 | 読む量 | 頻度 |
|---|---|---|
| 解析（256px サムネイル） | 先頭 26KB（97.4%）／全体（2.6%） | 1 枚 1 回 |
| 解析（表示用） | **全体** | 1 枚 1 回 |
| 拡大表示 | 全体 | **利用者が押したときだけ**。取って捨てる |

厳選フォルダへのコピーも原本のバイトを流すが、チャンクで流すので端末には残らない。
選別画面・連写画面・比較画面・各種一覧は、**原本を一切読まなくなる。**

拡大表示まで原本から切り離すこともできる（表示用をさらに大きくする）が、サイドカーが膨らむ。拡大は利用者が意識して押す低頻度の操作なので、
**その 1 枚だけ原本を取る形を推奨**する。

### 端末の容量（実測にもとづく）

サムネイルの実測値: **6.6 KB/枚**（PC の `app_data_dir/thumbnails/` 821 枚 = 5.27MB）。

| 2,000 枚で端末に残るもの | サイズ |
|---|---:|
| 256px サムネイル | **13 MB** |
| SQLite | 約 3 MB |
| 表示用（既定 1024px） | 約 170 MB |
| **写真の原本** | **0** |

**原本は一度もディスクに書かない。** メモリに読んで解析し、捨てる（PC でも同じ）。

表示用サイズだけが枚数に比例して増えるので、**ここに LRU の上限を設ける**
（既定 300MB 程度、設定で変更可）。上限を付けると**端末の使用量がプロジェクトの
枚数に依存しなくなる**。2,000 枚でも 10,000 枚でも頭打ちになる。
実体は NAS のサイドカー（§6）にあるので、溢れても再取得できる。

### 端末にバイトが落ちうる場所は 3 つだけ。すべて上限を持たせる

| 場所 | 素直に作った場合 | どう抑えるか |
|---|---|---|
| 解析 | 原本を一時ファイルに落とす → 1 枚 6.7MB | **落とさない。** バイト列をメモリで扱う（§4 の `PhotoSource`）。ピークは 1 枚ぶんの約 7MB |
| 拡大表示 | 原本を一時ファイルに置いて asset プロトコルで表示 | **一時ファイルは 1 個だけ**を使い回し、閉じたら消す。上限 1 枚ぶん |
| 厳選フォルダへのコピー | 原本を落として再アップロード → 1 枚 6.7MB | **チャンクで流す**（読み 1MB → 書き 1MB）。ピーク約 1MB。SMB2 のサーバー側コピー（`FSCTL_SRV_COPYCHUNK`）が使えるなら**端末を 1 バイトも通さない**（要検証） |

### 方針

1. **サイドカーがあればそれを使う。** 解析ゼロ。これが常用の経路になるはず
2. 無ければ **先頭 64KB を読み、APP1 の長さを見て足りなければ不足分だけ追加で取る。**
   実測 26KB なので 64KB あればほぼ 1 往復で済むが、カメラによって変わるため
   固定長にはしない（512KB のような大きめの固定値は、20 倍の無駄になる）
3. それも失敗する写真（EXIF サムネイル非搭載の JPEG、PNG/WebP）だけ全体を落とす。
   `DecodeSource` が既に 3 経路を区別して記録しているので、**どの経路が何枚だったかは
   既存の `thumbnail_source` 列でそのまま見える**
4. 並列度は `MAX_ANALYSIS_WORKERS = 4` のままから始め、**実測で決め直す**。
   ローカルディスクと SMB では最適値が違う。上書き用の環境変数
   `PHOTO_CURATOR_WORKERS` が既にあるので、実機での調整はコード変更なしでできる

### 測り方

`src-tauri/src/bin/bench.rs`（`--features bench`）が Routine 1 で作られている。
**SMB 用のサブコマンドを 1 本足して同じ土俵で測る。** 上の推測値は必ず実測に置き換えること。

## 10. 検証方法

### 自動テストで担保する（実機不要）

| 対象 | どこで |
|---|---|
| `PhotoSource` 経由でもサムネイル・dHash が変わらない | Rust ユニット。**既存 53 件がそのまま回帰テストになる** |
| 部分読みで EXIF サムネイルが取れる | Rust ユニット。既存の `Fixture`（`tiff_block` / `write_jpeg_with_exif`）で先頭 N バイトだけを渡す |
| `PhotoRef` の文字列往復 | Rust ユニット。`content://` / `smb://` / ローカルパスの判別。**既存行がローカルとして解釈されること**を明示的に確かめる |
| サイドカーの読み書き | Vitest。`utils/sidecar.ts` を純粋関数にし、`updatedAt` が新しいときに上書きしないことを確かめる |
| 能力フラグによる UI 分岐 | Vitest。`groupSizeLimits` の入力が `isDesktop` から `capabilities` に変わること |
| SMB のパス組み立て・一覧の並べ替え | JVM ユニット（Kotlin プラグイン側）。**ネットワーク無しで通る部分だけ**を切り出す |

**すべてミューテーションテストを行う**（既存の作法）。特に:

- 先頭の取得サイズを足りない値（例: 8KB）にしたとき **追加取得に落ちる**こと。
  その追加取得を止めると EXIF サムネイルのテストが落ちること
- `PhotoRef` の判別で `smb://` と `content://` を入れ替えて落ちること
- サイドカーの `updatedAt` 比較を反転して落ちること

### 実機でしか確認できないこと（USB デバッグ）

前提: 開発者オプション → USB デバッグを ON、`adb devices` で端末が見えていること。

```bash
pnpm tauri android dev
```

| # | 手順 | 見るもの |
|---|---|---|
| 1 | 上のコマンドで実機に配信 | ホーム画面が出る。`adb logcat` にクラッシュが無い |
| 2 | 「プロジェクトを作成」→ フォルダ選択 | SAF のフォルダ選択が開き、選んだあと走査が始まる |
| 3 | アプリを終了 → 再起動 → 同じプロジェクトを開く | **再走査できる**（URI 権限が永続化されている） |
| 4 | 選別を開始 | 1 グループが **4 枚**で出る。キーボードの案内が出ない |
| 5 | 連写のまとまりを開く | 前後 4 秒の写真が並ぶ（Routine 7 の画面がそのまま動く） |
| 6 | NAS へ接続 → 走査 | 一覧が返る。`adb logcat` で 1 枚あたりの所要時間を確認 |

| # | リスク | 影響 | どう扱うか |
|---|---|---|---|
| 1 | **smbj を Tauri Android プラグインから使えるか未検証** | R13・R15 が丸ごと成立しない | **R12 のスパイクで最優先に確かめる。** ただしその前に §5 の「5 分で終わる確認」（WebAccess A が DocumentsProvider として現れるか）を必ず見る。**当たれば SMB の実装ごと不要になる。** 失敗したらその時点で相談する（利用者の決定）。選択肢として ① SAF 経由で NAS を読む ② jcifs-ng（LGPL 2.1 に注意） ③ PC に HTTP ブリッジ（`HttpBackend`）を記録に残す |

## 12. やらないこと

- **宅外アクセス（VPN / WebAccess）。** 今回は自宅 Wi-Fi 内でのみ動けばよい。
  必要になった場合の選択肢だけを残す:
  - ルーター側の VPN サーバー機能（**NAS には無い。ルーターの機能**）
  - WireGuard 等をアプリに組み込む（**アプリが端末の VPN プロファイルを作ることは
    OS の制約上できない**ので、自前実装になる）
  - Buffalo の WebAccess（**ポート開放が必須で NAS をインターネットに晒す。** API も非公開）
- **オフラインでの選別継続と反映キュー。** §8 のとおり。
- **ネイティブ Kotlin での作り直し（案 C）。** §2 のとおり。
- **iPad 版（`LocalBackend`）の挙動変更。** R9 の能力フラグが形式的に通るだけで、見え方は変えない。
- **写真原本を破壊する操作。** 厳選フォルダへは**コピーのみ**。既存の
  `export_by_rating` の `move_files`（原本を移動する）は **Android では露出させない**。
