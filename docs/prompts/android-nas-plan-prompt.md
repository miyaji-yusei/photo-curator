# 実装プラン作成プロンプト — Photo Curator の Android 対応と NAS 連携

以下をそのまま計画セッションに渡す。

---

あなたは写真選別アプリ **Photo Curator**（`C:\Users\miyaj\Documents\tools\photo-curator`）の実装プランを作成する。**実装はまだ行わず、プランのみを作る。**

## プロジェクトの現状

大量の写真を「軽い判断の繰り返し」で選別するアプリ。現在は Windows デスクトップ（Tauri）と、iPad のブラウザ単体の2形態で動く。

### 技術構成

- **Tauri 2 / Rust** — `src-tauri/`。SQLite(`rusqlite` bundled)、`image`、`kamadak-exif`、`jpeg-decoder`、`walkdir`
- **Nuxt 3 / Vue 3 / TypeScript / Vuetify 3 / Pinia** — 画面。`nuxt generate` で静的出力
- **Vitest**（191件）+ **Rust ユニットテスト**（53件）+ `nuxt typecheck`
- `src-tauri/Cargo.toml` の `crate-type` は既に `["staticlib", "cdylib", "rlib"]`

### アーキテクチャの要

`composables/photoBackend.ts` の **`PhotoBackend` インターフェースが、フロントとバックエンドの唯一の接点**。`app.vue` / `utils/*` / `types/*` はこれより下を知らない。実装は2つ:

| 実装 | 用途 | 保存先 |
|------|------|--------|
| `TauriBackend` | デスクトップ | PC の SQLite + 原本フォルダを走査 |
| `LocalBackend` | iPad などのブラウザ | IndexedDB + 写真ピッカー経由の取り込み |

インターフェースのコメントには、将来 PC のプロジェクトを遠隔選別する `HttpBackend` を足す想定が明記されている。**新しい写真ソースや実行環境は、このインターフェースの実装を増やす形で入れるのが設計の意図。**

### 主要な機能

- プロジェクト（写真フォルダ）を作り、走査してサムネイル生成・dHash・EXIF撮影時刻を解析
- トーナメント形式の選別（グループを見て通す/落とす、ラウンドを繰り返す）と星評価
- 連写（バースト）の検出 = 撮影時刻の窓 + dHash のハミング距離。**閾値はユーザーへの出題で学習**する
- 連写のまとまりは代表1枚だけを選別に出し、確定後に星を仲間へ配る
- 選別中に連写ダイアログでまとまりを分割/結合し、その形は `burst_pair_overrides`（ペア単位の例外）として永続化される
- 星ごとのフォルダへの書き出し、XMP への星の書き込み

### 開発の作法（踏襲すること）

- 作業単位ごとに `docs/progress/routineN.md` に「やりたいこと / 決めたこと / 素直に作ると壊れる箇所 / 実装したもの / 検証」を日本語で記録している
- ロジックは純粋関数に切り出し、ユニットテストで担保する（`utils/burstEdit.ts` が good example）
- **ミューテーションテスト**を行い、意図的にコードを壊してテストが落ちることを確認している
- コメントは「なぜそうしたか」を日本語で書く

## 今回のゴール

**Photo Curator を Android で使えるようにし、自宅 NAS の写真を選別対象にする。**

## 既に決まっていること（変更しない）

1. **NAS へのアクセスは Android から直接 SMB で行う。** PC を経由しない構成を第一目標とする
2. NAS 上の選別結果の反映先は、**NAS 上に「厳選」フォルダを作ってコピー**する方式（原本は変更しない）
3. 検証用の Android 実機があり USB デバッグが可能。**Android 13 以上**が対象
4. 写真原本を破壊する操作は行わない

## 調査済みの事実（再調査不要、前提として使う）

### NAS: Buffalo LinkStation LS710D

- 公式仕様で明記されているのは **SMB/CIFS・FTP・HTTP/HTTPS・DLNA/DTCP-IP**。NFS・WebDAV・SFTP は公式仕様書に記載がない（海外流通サイトには記載があるが未確認）
- **VPN サーバー機能は無い。** VPN サーバーは本来ルーター側の機能
- 宅外アクセス手段は **WebAccess**（BuffaloNAS.com の中継サーバー経由）だが、**ルーターのポート開放が必須**で NAS をインターネットに露出させる。API は非公開
- ユーザーの申告型番は `LS710DBD2` だが該当 SKU が見つからず、公式には `LS710D0101/0201/0401/0801`（容量違い）。シリーズ共通仕様のため設計判断は変わらないが、SMB のバージョン設定等は実機の管理画面で確認が必要

### Android の制約

- **アプリが端末の VPN プロファイルを作成することは OS の制約上できない**（デバイスオーナー/MDM 権限が必要）。アプリ内で VPN を完結させるには WireGuard 等の実装を自前で組み込む必要がある
- 自宅 Wi-Fi にいる間は **VPN 無しで SMB がそのまま通る**
- Android には任意のフォルダを走査する自由が無い。写真は **MediaStore** / **SAF (Storage Access Framework)** 経由になり、パスではなく `content://` URI で扱う
- 写真アクセス権限は Android 13 以上で `READ_MEDIA_IMAGES`。Android 14 には部分許可（`READ_MEDIA_VISUAL_USER_SELECTED`）がある
- システムのお気に入り（`MediaStore.MediaColumns.IS_FAVORITE`）は API 30+ で、`createFavoriteRequest()` にURIリストを渡せば確認ダイアログ1回で一括適用できる

### Tauri v2 と Android

- **Tauri v2 は Android を公式にサポートしている。** 本プロジェクトの `crate-type` は既に mobile が要求する `staticlib`/`cdylib` を含んでおり、`tauri android init` から始められる状態
- Tauri v2 では **Kotlin で Android プラグインを書いて Rust/JS から呼べる**。OS 固有 API（MediaStore、SAF、SMB ライブラリ）はこの仕組みで橋渡しできる

### Rust から SMB を扱う難しさ

- **成熟した純 Rust の SMB クライアントは存在しない。** `pavao` は libsmbclient への FFI で、Android 向けクロスコンパイルは困難
- 一方 **JVM には smbj（SMB2/3、Apache 2.0、純 Java）や jcifs-ng があり、Android で動作実績がある**
- したがって「Tauri の Android プラグインを Kotlin で書き、smbj を使って SMB を扱い、Rust/JS へ公開する」経路が現実的な候補になる。ただしこれは要検証

## プランで比較検討し、推奨を出すこと

**Android 対応の実現方式**を、以下3案について「既存資産の再利用度 / 実装量 / 性能 / OS連携の自由度 / 保守性」の観点で比較し、**推奨案を1つ明示する**こと。

| 案 | 概要 |
|----|------|
| A. Tauri v2 の Android ターゲット | 既存の Nuxt 画面と Rust コアをそのまま流用。写真アクセスと SMB は Kotlin プラグインで橋渡し |
| B. 既存のブラウザ版を Android Chrome で使う | `LocalBackend` をそのまま使う。追加実装はほぼ不要だが、写真ピッカー経由に限られフォルダ走査も SMB も不可 |
| C. ネイティブ Kotlin で新規開発 | Android 専用に作り直す。OS 連携は最良だが、選別ロジック・解析・DB をすべて再実装することになる |

比較にあたっては、**選別ロジック（トーナメント、連写判定、閾値学習、まとまり編集）と解析（dHash、EXIF、サムネイル）が既に十分な量とテストを伴って存在する**ことを重く見ること。

## プランに必ず含めること

1. **推奨方式とその理由**（上記3案の比較表を含む）
2. **`PhotoBackend` をどう拡張するか**。Android 用の実装を新設するのか、既存2実装のどちらかを分岐させるのか。インターフェースに変更が要るなら、その差分と既存2実装への影響
3. **写真ソースの取得経路**。端末ローカル写真（MediaStore/SAF）と NAS（SMB）の両方をどう `PhotoBackend` に載せるか。`content://` URI とパス前提の既存コードの齟齬をどう吸収するか
4. **SMB 実装の具体案と、最初に行うべき技術検証（スパイク）**。smbj を Tauri プラグイン経由で使う案の実現可能性を、実装前に最小コードで確かめる手順
5. **解析の実行場所と性能**。SMB 越しに数百〜数千枚のサムネイル生成と dHash を行うときの転送量・所要時間の見積もりと、キャッシュ戦略（一度解析した写真を再解析しない仕組みは既にあるか確認して活かす）
6. **オフラインでの扱い**。NAS に繋がらない場所でも、解析済みのサムネイルとスコアを見て選別を続けられるようにするか。厳選フォルダへの反映を後から実行するキューが要るか
7. **段階分けされたタスクリスト**。1タスク = 1つのまとまった変更で、それぞれに「変更するファイル / 受入条件 / 依存する先行タスク / 規模(S/M/L)」を付ける。既存の Routine 方式（`docs/progress/routineN.md` への記録）に沿うこと
8. **各タスクの検証方法**。自動テストで担保できる部分（純粋関数・JVM/Rust ユニットテスト）と、実機でしか確認できない部分を明確に分ける。実機確認は USB デバッグ前提の具体的手順で書く
9. **リスクと未確認事項**。特に SMB の実現可能性、Tauri Android の成熟度、モデル/ライブラリのライセンス、NAS の実機設定（SMB バージョン、認証方式）
10. **やらないことの明示**。宅外アクセス（VPN / WebAccess）は今回の対象外とし、必要になった場合の選択肢だけを記録に残す
