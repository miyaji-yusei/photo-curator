## 1. ユーザーフローの一覧

利用者の目的は 1 つ: **大量の写真から残す写真に★を付け、それを使える形で持ち出す**。そのための流れを 9 本に分けた。

```
F1 作る ─→ F2 準備（裏で自動）─→ F3 選別 ─→ F4 結果・★の手直し ─→ F5 書き出し・メタデータ
                 ↑                    ↕ F6 別の端末と続ける（サイドカー）
          F7 設定（表示用画像の px・RAW の組）        F8 やり直し　F9 削除
```

### F1 プロジェクトを作る

| | PC | Web | Android |
| --- | --- | --- | --- |
| 入口 | ホーム「プロジェクトを作成」→ `CreateDialog.vue` | 同じ | ホーム → `Create.kt`（タブ: 端末のアルバム・NAS・Amazon） |
| 出所 | フォルダ（NAS も Windows のフォルダとして）・Amazon 共有リンク | フォルダ（File System Access）・ピッカー（iPad）・Amazon（中継があるとき全部、無ければ表示だけ）・開発用 HTTP | 端末のアルバム（MediaStore）・NAS（SMB 直）・Amazon |
| 作成時に決めるもの | 名前・表示用画像の px（U13）・RAW の組（`createPairRaw`） | 同じ | 名前・出所。px はアプリの既定から（U20 以降は「…」で変える） |
| 作ったあと | 開く → 写真が 0 枚なら走査を自動で始める（`useCurator.ts:657-661`） | フォルダは同じ。ピッカーは「写真を追加」待ち（`ProjectView.vue:152-158`） | 開くと `Preparations.ensure` が走査から始める（`Album.kt:162-185`） |

**つまずきやすい所**
- Web のフォルダは**許可が切れる**。開いたときには求めない（利用者の操作の中でしか通らない）ので、詳細の「フォルダへのアクセスを許可」を押してもらう（`useCurator.ts:651-655`・`ProjectView.vue:56`）
- Amazon のリンクが消えたプロジェクトは開くたびに読みに行かない（`useCurator.ts:656-665`）。「再試行」だけが読む
- Android で NAS・Amazon を開いただけでは「止まっています」になる件は U43 で直した（1 回の失敗で諦めていた）

### F2 準備（走査 → 撮影時刻・サムネイル・ハッシュ値 → 表示用画像 → 連写の候補）

設計書 03 章「準備の 5 作業」（scan・meta・hash・display・sidecar）。**利用者が押すものは無く、開いたら裏で進む**のが仕様（01 章「準備」）。

| | PC | Web | Android |
| --- | --- | --- | --- |
| 走査 | `start_project_scan` → `scan.rs`。200 枚ごとのトランザクション（U37）。中身で画像でないものは `is_missing=1`（`analysis.rs:33-43`） | `prepareFolder`（`local.ts:335-394`）。走査が終われば `scan` を complete にして解析へ | `Photos.listing` → `Prepare.settleListing`（欠けた一覧なら控えを触らない。U50） |
| 撮影時刻 | 先頭 64KB の EXIF → 名前 → 更新時刻（`capture.rs:116-132`） | 解析の中で（`analyzePhoto.ts:128`） | 端末は MediaStore、NAS は EXIF（`Fingerprint.takenAt`） |
| ハッシュ値・サムネ | **連写の候補（時間の近いもの）だけ**（`analysis.rs:350-371`）。Amazon は全部 | **全部**（`local.ts:319-328`） | 全部（`Analyse.kt:225-323`） |
| 表示用画像 | 別の段（`display.rs`）。原本を全部読む | 解析と同じ復号で一緒に作る（`analyzePhoto.ts:153-160`）。`getDisplayBacklog` は常に 0（`local.ts:895`） | NAS・Amazon だけ作る（`Renders.kt`）。端末のアルバムは OS の絵 |
| 進みの見せ方 | 画面上の帯（`app.vue:152-158`）＋詳細の 3 行（`prepareProgress`） | 同じ | 詳細の「準備中」とホームのカード（`Home.kt:394-418`） |
| 失敗の見せ方 | 「◯件を解析できませんでした」の帯（`app.vue:160-162`）。件数は DB の `analysis_error` の行数（`analysis.rs:159-168`） | 同じ帯。ただし**件数はその回に失敗した数だけ**（`local.ts:292-314`） | **出さない**（失敗は控えず、次に開いたときにまた試す。`Analyse.kt:247-249`） |

**状態の遷移（PC・Web）**: `project.status` が `new → scanning → ready`（`missing` は出所が無い）。解析は `analysisProgress.phase` が `indexing/metadata/hashing → complete|cancelled|error`。走査中は `taskDialog` が開き、閉じるまで `startScan`・`beginTournament` は何もしない（`useCurator.ts:764`・`801`）。

**つまずきやすい所（実機の報告と読んだ結果）**
- **「準備中」が終わらない**: PC は解析に失敗した写真を「未処理」に数え続ける（`lib.rs:557-594` の `stale` は `d_hash IS NULL` を含む）。開くたびに `backlog > 0` で解析を起動し（`useCurator.ts:674`）、同じ失敗を繰り返す。Android も同じ（`Home.kt:399-405` は「ハッシュ値の数 < 顔ぶれの数」で準備中）。Web だけは失敗した行を数えない（`local.ts:800`）＝**3 実装で数え方が違う**。→ U58
- **「近い構図を比較しています」が遅い**: RAW を丸読みしていた（U55 で直した）。ただし**表示用画像の段はまだ RAW・HEIC を丸読みして失敗し、開くたびにやり直す**（§4 B1）
- **解析エラーの件数がおかしい**: PC の二重計上は U55 で直した。Web は回ごとの数なので、開き直すと 0 に見える。帯はプロジェクトを替えても残る（§4 B6）
- 解析エラーの**中身（どのファイルか・なぜか）を見る手段が無い**（3 実装とも）。→ U58

## 2. フローから見たコード構造の評価

### 2.1 フローごとのモジュールのまたがり

| フロー | PC・Web で通るもの（順） | 往復（backend の呼び出し） |
| --- | --- | --- |
| プロジェクトを開く | `openProject`（useCurator）→ `loadPreview`（usePreviewGrid）→ `runSidecarCheck`（useSidecarActions → useSidecarSync → backends）→ `loadSession` → `healRowRatings`（getCoreInputs・saveSelectionResults）→ `getAnalysisBacklog`・`refreshDisplayState`・`loadSummary` → `startBackgroundAnalysis`・`startDisplayGeneration` | サイドカーの確認だけで `getCoreInputs`・`getPairOverrides`・`loadSession`・`listProjects`・`loadSidecarState`・`deviceIdentity`・`getMissingRatings`・`readSidecar`（`useSidecarSync.ts:266-302`）。開く全体で**約 15 回**。`getCoreInputs`（全行）が確認と自己修復で **2 回** |
| 選別を開始 | `enterMethod` → 設定 → `beginTournament`（`syncAtBreak` → `loadSummary` → 確認）→ `startTournament` → `finishTournamentStart`（`resetSelectionResults` → `loadCoreInputs` → `loadPairOverrides` → core.startRound → `openSelection` → `enterStage` → `getPhotosByIds` → `saveSession`） | サイドカー（上の 8 回前後）＋ 6 回。`getCoreInputs` がまた 1〜2 回 |
| 1 タップ | `advanceWith` → core → `applyCore`（`saveSession` を待ち行列へ・`writeRatings` は待たない）→ `loadCurrentPhotos`（先読みが当たれば 0 回） | 書き込み 2 本（待たない） |
| 準備の進み | 進みのイベント（`mount` の中の listener。`useCurator.ts:1541-1587`）→ `refreshPrepareCounts`（1 秒に 1 回 `getAnalysisBacklog`・`getDisplayBacklog`）→ Web だけ `refreshDuringPreparation` | イベントごとに最大 2 回 |
| ホームのカード | `refreshProjectCards`: プロジェクトごとに 5 本（backlog 2・Session・集計・見本 1 枚）。`useCurator.ts:351-383` | プロジェクト数 × 5 |

**評価**
- 「開く」は**同じ全行（getCoreInputs）を 2〜3 回読む**。4,000 枚で PC は JSON の 4,000 行 × 回数、Web は rowCache が効く（`store.ts:97-111`）。害は小さいが、§2.5 R4 の「準備の状態を 1 回で返す口」と、サイドカーの `buildWith` に読んだ行を渡す形にすれば減る
- 進みのイベントの受け口（`mount` の 50 行）が、走査・解析・表示用・サイドカーの後始末を全部持っている。フローの境目（走査が終わった → 表示用を起動 → サイドカーの保留を確かめる）がここに埋まっていて読みにくい

### 2.2 3 回書いている規則（core に寄せられるか）

| 規則 | PC（Rust） | Web（TS） | Android（Kotlin） | 食い違い | core に寄せるか |
| --- | --- | --- | --- | --- | --- |
| 写真の対象（拡張子） | `scan.rs:25-33`: jpg jpeg png webp heic heif ＋ RAW 7 種（**rw2・pef・srw なし**）＋中身で画像か判定 | `folderScan.ts:41-54`: **拡張子で絞らない**（隠し・動画以外は全部） | `Smb.kt:66`・`Photos.kt:152`: jpg jpeg png webp ＋ RAW 10 種（**HEIC なし**） | **3 つとも違う**（§4 B4・B8） | **寄せる**（純関数 `is_photo_name`。中身の判定は環境ごと）。ただし顔ぶれが変わるのでユーザー決定が要る |
| 組の RAW を外す | `skip_paired_raw`（`scan.rs:47-`） | `skipPairedRaw`（`folderScan.ts:63-87`） | `RawFiles.skipPairedRaw` | 同じ（U46・U49 で揃えた） | 寄せる（挙動不変。試験の共通フィクスチャで縛れる） |

2. **表示用画像の失敗を覚えない**（PC）。毎回やり直す（§4 B1）
3. **枚数の数え方が 3 通り**: PC は「欠損でない行」、Web は「走査で見つけたファイル数（画像でないものも含む）」、Android は「一覧の長さ」。準備の進み（`prepareProgress`）は `photoCount - backlog` なので、失敗の数え方の違いがそのまま進みの違いになる

### 3.3 変更案（移行は書かない。ユーザー決定）

**DB-1 解析の失敗に種類を持たせる（U58 の本体）** — 優先: **高**
- 理由: ずれ 1・3。「非対応形式は再試行しない・数に含めない」「一時的は再試行」を決めるには種類が要る
- 形: PC `photos.analysis_error_kind TEXT NULL`（`'transient' | 'unsupported'`）。Web `StoredPhoto.analysisErrorKind?: 'transient' | 'unsupported'`＋失敗したときの `analysisFailedSize?`・`analysisFailedModified?`。Android 新しい控え `unsupported-<SHA>.json`（`{ relativePath: { size, version, reason, at } }`）
- 移行の考え方（手順はユーザー決定）: PC は `add_column_if_missing` で足すだけ（既存の失敗の行は種類が NULL＝**一時的として 1 回やり直し、そこで分類される**）。Web は行に項目を足すだけで版は上げなくてよい（無い＝一時的）。Android は新しいファイルなので既存に触らない
- 既存データへの影響: 既存の失敗が 1 回だけ再試行される（RAW は U55 で丸読みしないので軽い）。星には触れない
- 3 実装とサイドカーへの波及: サイドカーには載せない（端末の能力の差。PC は RAW を読める・Android は読める、など）。ただし**非対応の写真を選別から外すと、その写真はこの端末の `known` に入らない**ので、ほかの端末の★がそのまま採られる（D3 の規則。安全側）。**PC・Web で写真の行を `get_core_inputs` から外すと、サイドカーの `photos` からその★が消える**（`useSidecarSync.ts:276-277` が行から作る）ので、行は返して印を付け、`refs` でだけ外す（§5）
- 危険: 一時的な失敗を恒久と誤って分類すると、その写真が黙って選別から消える。分類は**安全側（迷ったら一時的）**。一覧で見えるようにする（U58）

**DB-2 表示用画像の失敗を覚える（PC）** — 優先: **高**
- 理由: ずれ 2・§4 B1（開くたびに RAW・HEIC を丸読みして失敗）
- 形: `photos.display_error TEXT NULL`・`display_error_kind TEXT NULL`（または DB-1 の種類を共有して「非対応なら表示用も作らない」）。原本が変わったら消す（`upsert_photo` の CASE に足す）
- 影響: 既存データは NULL＝今どおり 1 回は試す
- 波及: Web は解析と同じ行なので不要。Android は `Renders` の失敗を覚えていない（**推測**: 同じ問題がある。未確認）
- 危険: U57 で RAW は埋め込みプレビューから表示用画像を作れるようになる見込み。そうなると対象は HEIC（PC で復号できない）と壊れたファイルに絞られる

**DB-3 Android の控えのファイル名を衝突しない名前に** — 優先: **高**（§4 B2）
- 形: `listing-`・`fingerprints-`・`trouble-`（と新しい `unsupported-`）の名前を `CacheName.of(sourceKey)`（SHA-256 の 32 桁）にする
- 移行の考え方: 新しい名前が無く古い名前があれば読む（古い名前は衝突しうるので、**中の顔ぶれが出所と合うかを確かめてから**使う／合わなければ捨てて走査し直す）
- 影響: 衝突していた利用者は、一度だけ走査とハッシュ値の作り直しになる
- 波及: Android だけ。サイドカーの `photoKeys`（`Sidecar.kt:233-234`）が正しい顔ぶれを使うようになる
- 危険: 古い名前を消すタイミング（同じ出所の別プロジェクトがまだ古い名前を読んでいる間に消さない）

**DB-4 写真の枚数の意味を「選別の対象の数」にそろえる** — 優先: 中（U58 と一緒に）
- 形: PC `recount_photos`（`analysis.rs:63-77`）を `is_missing=0 AND 種類≠非対応` に。Web は解析の終わりに `photoCount` を行から数え直す。Android は `known.size - 非対応の数`
- 影響: ホームの「◯枚」が減る（非対応の数だけ）。U58 の決定どおり
- 危険: `photoCount === 0` で走査を自動で始める判定（`useCurator.ts:658`）が、**全部が非対応のフォルダ**で毎回走査を始める。条件を「走査したことがあるか（`status`）」に替える

**DB-5 Web の写真の行に大きさ・更新時刻を持つ** — 優先: 中
- 理由: ずれ 4。原本が変わったら作り直す（03 章）・非対応形式の「原本が変わるまで再試行しない」を Web でも守る
- 形: `StoredPhoto.size?`・`lastModified?`（解析で `File` を読んだときに入れる。走査では取らない＝W10 の速さを保つ）
- 影響: 既存の行は無い＝今どおり
- 危険: 走査で取らないので「変わった」は**解析し直すときにしか分からない**。非対応の行だけ、再読み込みのときに `getFile()` で確かめる（少数なので速さの問題は無い）

**DB-6 ハッシュ値・サムネイルを出所ごとにする（PC・Web）** — 優先: 低
- 理由: ずれ 5。同じフォルダの 2 プロジェクトで準備が二重
- 形: PC は `photo_analysis(source_key, relative_path, fingerprint…, d_hash, thumbnail…)` を分け、`photos` はプロジェクトの顔ぶれと★だけにする
- 影響: 大きい（解析・表示・削除のほぼ全部の SQL）。仕様と合うだけで、利用者の困りごとの報告は無い
- 危険: 削除（「同じ出所の他のプロジェクトが無ければ絵を消す」。03 章「いつ消すか」）の規則が要る。**今はやらない**を推奨

**DB-7 写真の id を相対パスから決める（PC・Web）** — 優先: 低
- 理由: ずれ 8。対応表が要らなくなる
- 影響: サムネイル・表示用画像のファイル名が全部変わる。利点が小さい。**今はやらない**を推奨

## 5. U58 の実装メモ

**決定（ユーザー）**: (a) 解析できなかったファイルを、警告から**名前と理由の一覧**で見られる。(b) **非対応形式**（壊れた・読めない形式）は**原本が変わるまで再試行しない**。NAS の瞬断など**一時的な失敗は再試行**する。(c) 非対応形式は**準備の進みと選別の対象の枚数に含めない**。

### 5.0 3 実装で共通の規則（このメモでの決め。迷ったら安全側＝一時的）

| 失敗 | 種類 | 理由 |
| --- | --- | --- |
| ファイルを開けない・読めない（stat・読みの I/O エラー、許可、NAS の切断） | 一時的 | 次に開いたとき・再読み込みで直りうる |
| 1 枚の打ち切り（15 秒）・ワーカーの異常終了 | 一時的 | NAS の遅れ・メモリ |
| Amazon の取得の失敗（網・404 以外） | 一時的 | リンクの更新で直る（404 は今どおりプロジェクトごと `missing`） |
| **全部読めたのに復号できない**（形式が非対応・壊れている）、RAW で埋め込みのプレビュー・サムネイルが取れない | **非対応** | 原本が変わらない限り何度やっても同じ |
| ハッシュ値だけ作れない（画像が小さすぎる。Web） | 失敗にしない（今どおり。絵はあるので選別できる） | — |
| 中身が画像でない（PC の `content_is_not_image`） | 今どおり `is_missing=1`（数えない・一覧にも出ない） | — |

- 「原本が変わった」: PC は `fingerprint_mtime/size`（再走査の `upsert_photo` が違えば `analysis_error` を消す。`scan.rs:193-194`）。Web は失敗したときの `File.size/lastModified`。Android は `Photo.size`（`Fingerprint.size` と同じ考え）
- **選別から外すのは新しく組むときだけ**（`startRound`・`next_round`・`round_for` に渡す `refs`）。**途中の Session に入っている写真は表示できるよう対応表に残す**（行を消すと `idOf` が引けず、組の写真が欠ける）
- **星は消さない**。非対応の写真に★があれば（サイドカーから来た等）、サイドカーの `photos` に載せ続ける

### 5.4 試験（3 実装とも、先に赤を確かめる）

- 一時的な失敗は次の実行で再試行される／非対応は再試行されない／原本が変わったら（PC: 大きさ・更新時刻、Web: `File` の大きさ・更新時刻、Android: 大きさ）再試行される
- 非対応は backlog・準備の進み・`photoCount`（DB-4 を採るなら）・`refs` に入らない。途中の Session に入っている非対応の写真は、組の表示で引ける
- 非対応の写真の★（サイドカー由来）が、こちらの端末が書いたサイドカーに残る（PC・Web: `buildWith` の `photos`）
- 一覧の口が名前・理由・種類を返す
- 既存の失敗（種類 NULL）は 1 回だけ再試行され、そこで分類される

### 5.5 ユーザーに確かめたいこと（U58 の実装は止めずに、仮置きで進めてよいもの）

1. 「ハッシュ値だけ作れない（小さすぎる）」写真を失敗の一覧に出すか（仮置き: 出さない。数えない）
2. Amazon の受け取った画像が復号できないときを非対応にするか（仮置き: 一時的）
3. `photoCount`（ホームの「◯枚」）から非対応を引くか（仮置き: 引く。DB-4。U58 の決定 (c) の素直な読み）
4. Web の写真でないファイル（B4）を拡張子で外すか（仮置き: U58 では外さない。非対応として一覧に見える）
