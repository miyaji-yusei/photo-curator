## 取り込み方針（main を土台に）

> 2026-09-29 調査（クラウドのセッション。Obsidian・Windows・NAS・Amazon に届かない環境だったので、**このノートは会話から貼り付けて転記**する）。
> 比べたもの: **旧版 = `main`（2275d05）**、**新版 = `origin/feat/rebuild`（a9f1359。PR #3 `feat/amazon-web-relay` を含む）**。main から 124 コミット先（docs を除くと約 110）。
> 方針: 旧版を土台にして、新版で足した機能のうち要るものだけを取り込む。**main ブランチは汚さない**（作業は新しいブランチ `feat/main-base` で行う）。

### 1. 実測値

**測った環境**: クラウドの Linux（4 コア・15GB）と、ヘッドレス Chromium（Playwright）。
**写真**: 合成した JPEG 454 枚（4000×3000、1 枚約 2.4MB、EXIF の撮影時刻と 160×120 の埋め込みサムネイル付き、連写に近い並びを含む）。置き場所はローカル SSD。
**測れなかったもの**: NAS・Amazon 共有リンク（プロキシで 403）・Tauri の窓（画面が無い）。PC 版の値は、`src-tauri` の画像処理のソース（`image_pipeline.rs`・`exif_util.rs`）をそのまま取り込んだ計測用プログラムで測った。

### 2. 遅い理由（コードで説明する）

**① 新版は、表示用画像が全部できるまで選別を始められない（最大の原因）**

- 新版の `pages/project/[id]/index.vue:173` は `needsPrepare = scannedCount < photoCount || displayedCount < scannedCount`。この間、主ボタンは「準備を始める／準備中…」のまま。
- 表示用画像のない写真は、選別画面で `v-if="displayUrls[path]"` によって空のタイルになる（`cull.vue:560`）。
- 旧版の `app.vue` の `beginTournament`（「解析の完了を待たない。…未解析が残っていても選別画面へ進む」）は、走査が済めば選別に入れる。表示用画像は裏で作る（`start_display_generation`・`AnalysisMode::Background`）。
- 旧版の絵は `photoDisplayUrl` が **表示用 → サムネイル → 原本** の順に落ちる。そのため絵が空になることが無い（旧 `composables/backends/tauri.ts`）。
- FR-2.3「走査が終わるまで選別は開始できない。それ以外は未完でも開始できる」に合っているのは旧版の方。

**② PC の開発実行（`tauri dev`）は画像処理が 35 倍遅い**

- 上の表のとおり。旧版も同じ条件だが、①のおかげで待たされないので、遅さが見えなかった。
- 新版は①のせいで、この遅さがそのまま待ち時間になる。110 枚に 8 分かかった記録（07章 段4-2）と合う。
- 直し方は `src-tauri/Cargo.toml` に `[profile.dev.package."*"] opt-level = 3` を足すこと。依存ライブラリだけ最適化され、自分のコードのビルドの速さは変わらない。

**③ 新版の Web の準備は直列で、ワーカーを使っていない**

- 旧版の `local.ts` は `analyzeAll`（ワーカー 3 本）を使う。新版は `webFolder.ts` も `webPicker.ts` も 1 枚ずつ。実測で 3.2 倍の差。

**④ 新版は写真ごとに IPC を往復して URL を得る**

- 新版の `thumbnailUrl`・`displayUrl` は、1 枚ごとに `invoke('thumbnail_path')`・`invoke('display_path')` を呼ぶ。Tauri の同期コマンドはメインスレッドで動く。
- `originalUrl` は、そのたびに `getProject`（`projects.json` 全体を読む）も呼ぶ。
- 旧版は写真の行に `thumbnailPath`・`displayPath` が入っていて、`convertFileSrc` を**同期で**組み立てる。IPC は 0 回。

**⑤ 新版は、重い同期コマンドがメインスレッドで動く**

- `amazon_original`（原本をネットから取る）・`amazon_preview`（共有リンクを歩く）・`sample_folder`（NAS で 12 枚を読む）・`list_entries` は、どれも `async` でも `spawn_blocking` でもない。
- そのため、動いている間は窓全体が固まる。
- さらに `amazon_original` は、原本のバイト列を `Vec<u8>` のまま JSON の数値配列で返す（3MB → 約 12MB の JSON）。`sample_folder` の見本 12 枚も同じ返し方。

**⑥ 新版は走査で全ファイルを開く**

- 新版の `scan` は 1 ファイルごとに先頭 16 バイトを読んで形式を判定する。NAS では 1 枚 33ms（実測。並列化後で 2.5 秒/110 枚）。その後の `meta` でもう一度開く。
- 旧版は拡張子と `metadata()` だけで数える。
- 07章の決め（「中身の先頭バイトで判定」）は守りつつ、**判定を `meta` の 64KB 読みに相乗りさせれば** 1 回の往復で済む。

**⑦ 新版は保存が「まるごと書き直し」**

- `photos.json`・IndexedDB の `photos:<id>` を、20 枚ごとに配列ごと書き直す。4,000 枚だと 200 回 × 約 1MB。
- 1 タップごとの `save_session` も、`session.json` 全体を pretty JSON で書き、さらに `sidecar-state` も書く。
- 旧版は PC が SQLite（行単位・ページ単位）、Web が IndexedDB の写真ごとの行。
- 454 枚では体感の差は出なかった（Web のタップ 80ms）。4,000 枚で効いてくる種。

**⑧ 新版は詳細画面を離れると準備が止まる**

- `pages/project/[id]/index.vue:169` の `onUnmounted(() => abortController?.abort())` がある。そのため、選別画面や結果画面へ移ると表示用画像づくりが止まり、戻ると 20 枚単位の続きからやり直しになる。
- 07章 2026-09-09 の決め「準備の持ち主はアプリ。詳細画面を離れても続く」と食い違っている。
- 旧版は Rust 側の `TaskRegistry` が持ち主なので、画面を移っても続く。

**逆に、新版の方が良いところ**

- Web の選別の反応（80ms 対 113ms）。
- 結果画面の遅延読み込み（T7 の `IntersectionObserver`）。
- 判断を core（Rust）の 1 か所に置いたこと。Android と答えが揃う（NFR-7）。旧版の `utils/tournament.ts` は Android と規則が分かれている。
