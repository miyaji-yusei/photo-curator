## Rust の中核を Kotlin から呼べるか（2026-09-07）

**通った。**

| 確かめたこと | 結果 |
|---|---|
| `core` クレートが UniFFI 込みで組める | ✅ テスト 9 件 |
| **Android 向け `.so` が出来る** | ✅ **612KB**（いまの Tauri の `.so` は 157MB） |
| Kotlin のバインディングが生成される | ✅ 1,459 行。`groupBursts(photos, threshold, overrides)` として呼べる |

生成された Kotlin はこの形になる。

```kotlin
fun groupBursts(
    photos: List<PhotoRef>,
    threshold: BurstThreshold,
    overrides: List<PairOverride>
): List<BurstGroup>
```

**手書きの JNI が丸ごと不要になる。** いまは `JNI_OnLoad` で JavaVM を取り、
クラスをキャッシュし、例外を払い、JSON で受け渡している。UniFFI は
それを全部生成する。2026-09-06 に踏んだ JNI の不具合（JavaVM が取れない、
`FindClass` がワーカースレッドで効かない、例外が握り潰される）は、
どれもこの手書き部分にあった。

### 大きさの比較

| | 大きさ |
|---|---|
| いまの Tauri の `.so`（WebView・Nuxt 一式を含む） | 157MB |
| **core だけの `.so`** | **612KB** |

APK 337MB の大半は WebView と埋め込みの画面。ネイティブにすれば消える。

### やり方の注意

- `uniffi-bindgen` は**同じクレートの中に小さな bin を置いて**呼ぶ
  （`src/bin/uniffi-bindgen.rs`）。別途入れるとクレートと版がずれて、
  生成物と実行時ライブラリが噛み合わなくなる
- `cargo-ndk` は要らない。既存の `scripts/android-apk.mjs` と同じく、
  NDK のツールチェインを環境変数で cargo に渡せば `--target` で組める

## 実機で通した（2026-09-07 03:42）

**Kotlin から Rust の core が動いた。** `groupBursts` が「80 枚・80 グループ」を返した
（dHash をまだ作っていないので全部が単独になるのが正しい）。

### loadThumbnail の実測 — **これが一番大きい**

```
loadThumbnail(512px): 30 枚を 104ms（1 枚 3.5ms、成功 30、平均 72KB）
```

| | Tauri 版（自分で作る） | ネイティブ（OS に任せる） |
|---|---|---|
| 1 枚 | 原本 6.7MB を読んでデコード | **3.5ms、読み込みは OS 任せ** |
| 2,000 枚 | **13.4GB を読む** | **7 秒** |

**「サムネイルを作る」という工程が丸ごと要らなくなる。**
`meta` と `hash` のために原本の先頭を読む必要は残るが、
表示のための縮小画像を自前で持つ理由が消える。

§01 のデータモデルから `thumb_path` / `thumb_of_size` / `thumb_of_mtime` を
落とせる見込み。**持たないものは壊れない。**

### 途中で踏んだこと（次に同じ所で止まらないように）

UniFFI の名前の規則が**ファイル名と記号で別**だった。

| | 規則 |
|---|---|
| 読み込むファイル | `libuniffi_<namespace>.so` |
| 引く記号 | `uniffi_<クレート名>_...` |

クレート名を `uniffi_` 付きにすると記号が二重前置きになって合わない。
**クレートはそのままにして、置くときにファイル名を付け替える**のが正解。
`scripts/build-core.mjs` がそれをやる。

権限を許可した直後にアルバムが 0 件のままだったのも直した。
権限のダイアログは別の Activity なので、**前面に戻るたびに読み直す**。
起動時に 1 回だけ問い合わせると、許可前の結果が残る。

ナビゲーションバーが明るい帯になるのは `windowLightNavigationBar` の
指定漏れだった。Tauri 版で「画面下部が白い」と言われたのと同じ現象。

## 2 回目（実機、Android 作り直し版）

### 連写が 1 組もまとまらなかった

原因は 3 つあり、**どれも「動いていないことに気付けない」種類**だった。
まとまらない理由が「指紋が無い」「時間が離れている」「見た目が違う」の
どれなのか区別できないまま閾値を動かしていて、いつまでも直らなかった。
隣どうしの内訳をログに出すようにして、初めて切り分けられた。

```
隣どうし 79 組 / 両方に指紋 79 / 時間が近い 27 / 見た目が近い 0 / 両方 0
```

**1. 並び順と時刻が食い違っていた。**
MediaStore に `DATE_TAKEN` で並べさせていたが、この端末では
**2,257 枚中 1,497 枚が NULL**。実際に使う時刻は mtime に落としていたので、
並び順と比べる値が別物になっていた。連写は隣どうしでしか畳まないため、
どれだけ似ていても隣に来ない。使う値そのもので並べて直した。

**2. 縮小を Android に任せていた。**
`createScaledBitmap(src, 9, 8, true)` は縮小率が大きいと 2x2 しか読まない。
**同じ絵を JPEG で作り直しただけで距離が 5** 開いていた（閾値 6 のすぐ隣）。

これは「自己確認」で分かった。同じ絵の JPEG 往復を測れば、
写真が本当に違うのか指紋が壊れているのかが 1 行で分かる。

升目の平均を取る `d_hash_from_gray` を core に置き、各環境は輝度を
渡すだけにした。**同じ測り方で 距離 5 → 1。**
PC・Web と値が揃う前提も、これで初めて成り立つ（前は Android の
縮小器の癖がそのまま値に乗っていた）。

**3. 閾値を勘で置いていた。** → 下の表。

### まとめる基準の根拠

Camera 694 枚、4 秒以内に並ぶ 173 組の距離:

| 距離 | 組数 | 何か |
| --- | --- | --- |
| 0-4 | 6 | 連写 |
| 5-9 | 22 | 連写 |
| 10-14 | 15 | どちらとも言えない |
| 15-19 | 23 | 別の絵 |
| 20-24 | 17 | 別の絵 |
| 25-29 | 33 | 別の絵 |
| 30+ | 57 | 別の絵 |

指紋の揺れは 1。**9 を採り、迷う帯は切る側に倒した。**
非対称なコストがあるため: 間違えて繋ぐと片方が二度と画面に出ず、
選んだ覚えのない星が付く。切りすぎたときは両方見えるだけ。

結果、Camera は 694 枚 → 666 組。

### 速さ

| 何を | 結果 |
| --- | --- |
| 指紋 919 枚（温まった状態） | 3 秒未満（1 枚 3ms） |
| 指紋 919 枚（初回） | 30 秒弱（MediaStore が縮小画像を作る） |
| 2 回目に開く | 待ち時間なし（作り直さない） |

### OS の同意画面は当てにできない

`MediaStore.createFavoriteRequest` は同意画面を出す API だが、
**すでにその写真への許可を持っていると MediaProvider は黙って通す。**
実機では画面が何も出ないまま 4 枚に印が付き、ログに残ったのは

```
MediaProvider: User allowed grant for [4 items]
MediaProvider: Granted permission to 4 items on external
```

だけだった。**原本に触る操作の確認を OS に預けてはいけない。**
アプリ側で必ず一度止める。

## 絵の 3 段階（2026-09-08 決定）

**経緯。** 設計（`04-画面仕様`）は準備の 3 段目に「表示用画像（1024px）」を
置き、設定にも「標準 1024px（2,000 枚で 170MB）／大きく 1536px」があった。
これを**「ネイティブは OS の縮小画像を使うので不要」と判断して外した**のが
誤りだった。端末のアルバムには当てはまるが、**NAS には当てはまらない**。
端末なら原本のデコードは手元で数百 ms だが、NAS の原本は 1 枚 6MB を網越しに
読むので表示のたびには使えない。仕様が表示用画像を別工程として立てていたのは
まさにこのためで、外すべきではなかった。

そのうえ「選別画面は原本を読む」と決めたのが二重の誤りで、選別画面は 1 枚ずつ
6MB を待つことになり、絵が出なかった。連写判定画面は EXIF の 160x120 のままで、
判定できる画質ではなかった。

**決めたこと。** 絵は 3 段階に分け、役割を混ぜない。

| 段 | 何 | 大きさ | 実測 | 使う場所 |
| --- | --- | --- | --- | --- |
| サムネイル | EXIF の縮小画像 | 160x120 | 約 10KB | 詳細の一覧、まとまりの確認 |
| **表示用画像** | 原本を一度読んで縮小 | 長辺 1024/1536 | **約 80KB** | **選別・連写判定・連写シート** |
| 原本 | そのまま | — | 6MB 前後 | 拡大表示だけ |

- 表示用画像は**準備の 3 段目**として作る。**原本を読むのはここだけ。**
- **NAS のときだけ**作る。端末の写真は Coil が手元で要求サイズにデコードする
- 鍵と**ファイル名に大きさを含める**。設定を変えたときに古い小さい絵を
  出さないため
- 途中で止めても、できた分は残る（`.writing` に書いてから置き換える）
- 網に行けないときは、粗くてもサムネイルを出す。**何も出さないよりよい**

**取り違えを型で防ぐ。** 前は boolean 1 つで「原本かどうか」しか言えず、
選別画面が 160x120 を引き伸ばしていた。`SmbSize { Thumb, Display, Full }` に
分け、`Photo.thumbModel` / `displayModel(edge)` / `fullModel` の 3 つを
使い分ける。

### 実測（2021_06_13、187 枚、Wi-Fi）

| | 結果 |
| --- | --- |
| 表示用画像の作成 | 毎秒 1.6 枚（187 枚で約 2 分） |
| 1 枚あたり | 約 80KB（2,000 枚で約 160MB。設計の見積り 170MB とほぼ一致） |
| 2 回目に開く | 網に行かない。選別画面は即座に出る |

### つまずいた点

`AsyncImage` に `imageLoader` を渡し忘れた画面が 1 つあり、そこだけ何も
出なかった。既定の Coil は NAS の読み方を知らないので、**渡し忘れると
黙って空になる**。一括置換したときにコメント行が挟まっていて漏れた。
今後は「AsyncImage の数 = imageLoader の数」を確かめる。
