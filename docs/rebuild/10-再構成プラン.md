# 10 再構成プラン（main を土台に）

← [[Photo Curator 設計書]]　前: [[07 実装状況と残タスク]]（「取り込み方針（main を土台に）」節）

**この章は「どう組み直すか」と、その手順（T1〜）を書く。** 何を取り込むかは 07章の「取り込み方針」で決めた。
00〜06章の決めを変えるものは、§8 にまとめ、該当する章へ 1 行ずつ残す。

## 0. 前提

- **土台は旧版（`main` 2275d05）のコードと画面。** 新版（`feat/rebuild`）で足した機能を、旧版の画面の作法で移す（2026-09-29 ユーザー決定。新版は Android 版を PC 用に組み直したもので、PC・Web の画面は旧版の方が練れているため）
- **ブランチ**
  - 作業は `feat/main-base`（main から新しく作る）とワークツリー `../photo-curator-work` だけで行う。
  - **main も feat/rebuild も書き換えない。** 新版のコードは `git show origin/feat/rebuild:<path>` で読むか、新しく足すファイルに限って `git checkout origin/feat/rebuild -- <path>` で持ってくる。
  - push はユーザーの指示があるときだけ。
- **画面: 全部旧版。** 07章 Q1 の「混ぜる」はこの決定で置き換えた。新機能の入口（Amazon のタブ・サイドカーの表示・まとまり編集など）は旧版の見た目と言葉づかいで足す
- **PC の端末の保存: SQLite**（旧版）
- **GitHub Pages: 手動実行だけ**
- **判断: Rust の core を wasm で呼ぶ**（§2.1）。旧版の `utils/tournament.ts`・`burstAnalysis.ts`・`burstThreshold.ts` と、Rust 側の連写のまとめ（`get_burst_groups` ほか）は core に置き換える
- **将来の環境（2026-09-29 ユーザー回答）**
  - Chrome 拡張: **Amazon Photos の写真だけ**を選別する。
  - Swift Playgrounds: **Web の画面を包む薄い殻**。Android と同じく「端末の写真・NAS・Amazon」を全部扱う。
  - iPad は当面 Web（ピッカー）で使い、将来は Swift の殻に移る。
- **旧版がすでに持っている速さの作り（壊さない）**
  - 走査が済めば選別を始められる。表示用画像は裏で作る。
  - 絵は表示用 → サムネイル → 原本の順に落ちる。
  - SQLite に行単位で保存する。
  - Web はワーカー 3 本で並列に準備する。
  - 準備の持ち主は Rust の `TaskRegistry` で、画面を移っても続く。

## 2. 共有するものと、環境ごとに分けるものの境目

```
┌──────────────── 共有 ────────────────┐
│ core（Rust）: 星・連写・学習・Session・サイドカーの形と判定・ハッシュ値 │
│   ├ UniFFI → Android                              │
│   └ wasm（core-wasm）→ lib/core.ts → 画面               │
│ 画面（旧版の Nuxt。ルーターを使わない 1 画面の切り替え）         │
│ 型: types/photo.ts（旧版を core に合わせて直す）・lib/core.ts   │
└──────────────────────────────────┘
┌──────── 環境ごと（PhotoBackend の実装）────────┐
│ tauri  … Rust（SQLite・走査・画像づくり・Amazon・取り出し）   │
│ local  … Web。次の 4 つの部品を組み合わせる                  │
│   Store     : プロジェクト・写真の行・Session・設定（IndexedDB）│
│   BlobStore : サムネイル・表示用画像（IndexedDB。Swift はファイル）│
│   SourceIO  : 出所の一覧と原本のバイト（FSA / ピッカー / 開発用 HTTP / 将来は Swift の橋）│
│   Fetcher   : Amazon のバイト（中継 / 拡張の直接 fetch / Swift）│
└──────────────────────────────────┘
```

- **画像を作るのは環境の仕事。** PC は Rust の `image`、ブラウザ系は `createImageBitmap`（Safari は HEIC を読める）。ハッシュ値の計算（9×8 → 64 ビット）だけは core の `d_hash_from_gray`。
- **写真の鍵は「出所の中の相対パス」。** core の Session・サイドカー・Android がこの鍵で動くため。旧版の写真 id（uuid）は端末の中の行の鍵としてだけ残し、core に渡すときは `relativePath` に直す。
- **ルーターを使わない。** 旧版の `view` の切り替えを保つ。Chrome 拡張のページと WKWebView の `file`／独自スキームで、URL の書き換えに悩まずに済む。

## 3. 速さの要件（数値）

### 3.1 目標

| 何を | 目標 | 今（実測） |
| --- | --- | --- |
| 走査が終わってから選別を始められるまで | **走査の終わり＋1 秒以内**（表示用画像を待たない） | 新版: 表示用画像が全部できるまで待つ |
| タップしてから次の組が出るまで（NFR-1） | **100ms 以内（p90）** | Web 新版 80ms（p90 106ms） |
| 4,000 枚の詳細の格子のスクロール | 一度に置く DOM のタイルは **200 以下**・固まらない | 新版は 96 枚で打ち切り |
| Web の準備（454 枚・ローカル） | **25 秒以内**（旧版 23 秒と同等） | 新版 73 秒 |
| PC の準備（`tauri dev`） | release の **2 倍以内** | release の 35 倍 |

### 3.2 キャッシュ（絵の 3 段とハッシュ値）

| | PC | Web（フォルダ・ピッカー）・Chrome 拡張 | Swift Playgrounds |
| --- | --- | --- | --- |
| サムネイル 256px（約 15KB） | アプリのデータフォルダ `thumbnails/<project>/<fnv1a>.jpg` | IndexedDB `blobs`（キー `t:<project>:<path>`） | アプリの Caches |
| 表示用 1024px（約 100KB） | `display/<project>/<fnv1a>.jpg` | `blobs`（キー `d:<project>:<path>`） | 同上 |
| 原本 | 読むだけ（`convertFileSrc`）。Amazon は `amazon-cache/` に置き、閉じたら消す | フォルダ: handle から読み直す。ピッカー: その回だけ | security-scoped URL から読み直す |
| ハッシュ値・撮影時刻 | SQLite の `photos` の行 | IndexedDB `photos` の行 | JSON |
| 4,000 枚の容量 | サムネ 60MB＋表示用 400MB | 同じ。`navigator.storage.persist()` を求める | 同じ |

**表示の順**: 表示用 → サムネイル → 原本（ローカルのときだけ）。**空のタイルは出さない**（旧版の `photoDisplayUrl` と同じ）。

### 3.3 4,000 枚で固まらない条件

- **一覧は仮想化する**: 見えている行の前後 2 行だけを描く。タイルの URL は見えたときに 1 回だけ取る（`IntersectionObserver`。新版の結果画面（07章 2026-09-29 の T7）と同じ作り）
- **object URL は最大 300 個**まで保つ（`utils/objectUrlCache.ts`）。超えたら古いものから `revokeObjectURL`
- **並列数**
  - PC（ローカル）: `clamp(コア数/2, 2, 4)`
  - PC（UNC・ネットワークドライブ）: 2
  - Web: ワーカー 3 本。iPad（`largeGroups=false`）は 2 本
  - Amazon: 4
- **メモリ**: 選別画面が抱える表示用画像は「今の組＋次の組」まで（最大 20 枚）。iPad のタブで 300MB を超えないこと
- **保存は行単位**
  - 準備のチェックポイントは、変わった写真の行だけ書く（PC: `UPDATE`、Web: `put`）
  - 1 タップの保存は `session` の 1 行だけ。**画面の更新を先に、保存は後ろで直列の待ち行列**に入れる（FR-3.8 の「確定のたびに保存」は守る。保存の完了は待たない）
- **次の組の先読み**: 組を出したら、次の組の表示用画像を `new Image().decode()` で読んでおく
- **1 枚の打ち切り**: 準備で 1 枚に 15 秒以上かかったら飛ばして「読めなかった」に数える（旧版の `PHOTO_TIMEOUT_MS`）
- **重いコマンドはメインスレッドで動かさない**: Tauri の `#[tauri::command]` は `async fn` にし、中身は `spawn_blocking`（`list_entries`・`sample_folder`・`amazon_preview`・`amazon_original`・`export_*`・`storage_usage_bytes`・`estimate_delete_size`）。バイト列は JSON の配列で返さず、ファイルに書いてパスを返す

## 4. Backend の形

旧版の `composables/photoBackend.ts`（`PhotoBackend`）を土台に直す。**判断は持たない。**

- **消す口**
  - 連写のまとめ・学習の口: `getBurstGroups`・`getBurstPairs`・`saveBurstThreshold`・`clearBurstThreshold`・`getBurstNeighborhood`・`saveBurstShape`。core に移る。
  - `getSelectionSeed`。core の `start_round` が決める。
- **足す口**
  - `getCoreInputs(projectId)`: core に渡す写真の列。`{relative_path, captured_at, d_hash, d_hash_version}` を撮影順で返す。4,000 行を 1 回で。
  - `loadOverrides`・`saveOverrides`・`loadBurstDistance`・`saveBurstDistance`
  - `saveSession`・`loadSession`: core の `Session` の JSON をそのまま入れる。
  - サイドカー: `readSidecar`・`writeSidecar`・`loadSidecarState`・`saveSidecarState`。4 通りの判定は core の `sidecar_decide` と `useSidecarSync`。
  - `previewSource(source, limit)`: 枚数と見本 12 枚。
  - `amazonPreview?(url)`
- **残す口**（旧版のまま）
  - `getProjectPhotoPage`（ページ送り）
  - `photoThumbnailUrl`・`photoDisplayUrl`: 同期で、表示用 → サムネ → 原本の順に落ちる。
  - `moveRating`（星の一括移動）
  - `exportByRating`（コピーか移動）・`writeRatingsToFiles`
  - 準備の開始・中断の口
- **Web（`local`）の中は 4 つの部品に分ける**
  - `Store`（IndexedDB。新しい DB 名 `photo-curator-v3`）
  - `BlobStore`（サムネイル・表示用画像）
  - `SourceIO`（ピッカー／File System Access／開発用 HTTP）
  - `Fetcher`（Amazon のバイト。中継／拡張の直接 fetch）
  - Swift の殻では `BlobStore`・`SourceIO`・`Fetcher` を橋（`window.webkit.messageHandlers`）に替える。出所の型は `folder | picker | album | nas | amazon`（`album`・`nas` は殻のため。今は実装しない）。

## 6. 移行の手順（1 段 = 1 ブランチ = 1 PR）

### 運用

- **統合先は `feat/main-base`**（main から、2026-09-29 に push 済み）。main へは PR を出さない
- 段ごとに、直前の段のブランチ（最初は `feat/main-base`）から `feat/mb-tNN-<短い名前>` を切り、`feat/main-base` へ PR を出す
  - マージはユーザーが行う。
  - 前の段がマージされていなければ、前の段のブランチから切ってスタックする。PR 本文に「前の PR」を書く。
- **PR の概要に必ず書くこと**
  - この段でやったことと、確かめたこと（コマンドと結果）
  - ユーザーに頼む実機確認の手順
  - **次の段の手順**（ファイル・関数・確認方法・完了条件）
  - 残りの段の一覧
  - ローカルで続けるコマンド（`git fetch origin && git switch -c feat/mb-tNN-… origin/feat/mb-tMM-…`）
- 計画の正は Obsidian の 10章。`docs/rebuild/` はその写し。**段が終わるたびに両方を更新する**
- コミットの前に通すもの: `cargo test`（core）・`cargo check`（src-tauri）・`pnpm typecheck`・`pnpm test`
- ポート 3000 は使わない。`nuxt generate` の前に自分の開発サーバーを止める。CRLF。IndexedDB の版は下げられない
- プランと現実が食い違ったら、続けずに報告する

実リンク「嵐山」454 枚、ユーザー自宅の回線、PC は release ビルドの `amazon.rs` をそのまま呼ぶ計測用コード（`examples`。コミットしない）、Web はブラウザペインで `<img>` を読み込ませた時間。

- Web の ③④ は 454 枚を一度に `<img>` へ読ませた値（ブラウザが HTTP/2 で多重に取る。バイトは読めず、ハッシュ値は作らない）。アプリの実際の表示は見えたタイルだけ遅延で読むので、そのまま同じ土俵ではない。ブラウザのキャッシュを避けるため、測るたびに `viewBox` の値を変えた（163・166・167・1028〜1030 など。`160`・`1024` は PC が先に使った）
- 画像の取得（サムネ・表示用）に、デコード・縮小・保存（`image_pipeline`）は効いていない。デコードまで入れると 4 並列のサムネで 81.8 → 82.0 秒、表示用で 91.9 → 93.6 秒（誤差）。CPU は律速でない

**原因（実測の根拠つき）**
1. **ネットワークの待ちが律速。1 枚の往復が長く、同時に飛ばす数が 4 しかない。** 共有 agent で並列を 4 → 8 → 16 にすると 81.8 → 44.3 → 21.9 秒とほぼ反比例する。1 枚あたり約 0.7 秒（4 並列で 5.6 枚/秒）
2. **`agent()` を呼ぶたびに新しい ureq の agent を作っており、接続を使い回していない**（`fetch_image_bytes`・`fetch_children_page`・`fetch_share_root`）。tempLink は 302 で別ホスト（`cnt-02.content-jp.drive.amazonaws.com`）へ飛ぶので、**1 枚ごとに TCP＋TLS を 2 ホスト分やり直す**。curl での 1 枚は、新しい接続で約 1.0〜1.5 秒（TCP 接続だけで 0.32 秒）、同じ接続の 2 枚目以降は約 0.40 秒。agent を 1 つにするだけで、サムネ 122.3 → 81.8 秒（−33%）、表示用 175.2 → 91.9 秒（−48%）、一覧 2.97 → 約 1.35 秒
3. **Web が桁違いに速いのは、ブラウザが HTTP/2 の多重で同時に何百本も飛ばしているから。** Amazon 側（`www.amazon.co.jp`・`content-jp.drive.amazonaws.com`）は ALPN で h2 を返す。PC は ureq（HTTP/1.1 のみ）で同時 4 本。**同じ本数なら HTTP/2 に替えても往復の時間は縮まない**（待ちが律速なので、効くのは同時に飛ばす本数）
4. 小さいもの: 作成時の `preview()` が `list_photos` のあとに `fetch_all_children`（直下）をもう一度呼ぶので、一覧系を重ねて読んでいる。表示用は 16 枚ずつの組（`chunks(WORKERS*4)`）で区切り、組の最後の 1 枚を待つ間に worker が遊ぶ（実測はしていない。分は数秒〜十数秒の見込み）

**規約面の約束との関係**: 08章の §7・§11・§13 は、Amazon の読み込みを「並列 4（実測は 8 で問題なし。規約の『通常の利用』の範囲に収めるため控えめに）・同じ絵は二度取らない・本人の操作のときだけ」としており、コードは `amazon.rs` の `WORKERS = 4` と Android の `Amazon.PARALLEL = 4` に反映されている。**並列を 8〜16 に上げる案は、この約束を変える判断（ユーザー）が要る。** 下の「おすすめ」は約束の内側だけで済む。
