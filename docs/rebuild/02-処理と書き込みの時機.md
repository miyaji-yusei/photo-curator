# 02. 処理と書き込みの時機

**いつ読み、いつ書き、いつ消すか。** 今回の不具合はほぼ全部ここにあった。

---

## 5 つの作業

| kind | すること | 何を読む | 出来るもの |
|---|---|---|---|
| `scan` | フォルダ／アルバム／共有を数え上げる | 一覧だけ（中身は読まない） | `photos` の行 |
| `meta` | 撮影時刻と向き | **先頭 64KB** | `captured_at` `captured_from` |
| `hash` | サムネイルと dHash | 先頭 64KB（EXIF 埋め込み）、無ければ全体 | `thumb_path` `d_hash` |
| `display` | 選別に出す画像 | **全体** | `display_path` |
| `sidecar` | サイドカーの読み書き | `catalog.json` | 共有の反映 |

**読む量が桁で違う。** だから分ける。
`meta` は 1 枚 26KB で済み、`display` は 1 枚 6.7MB 読む（実測）。
混ぜると解析が桁で遅くなる（実測: 1.72ms/枚 → 132ms/枚）。

## 順番と依存

```
scan ──→ meta ──→ hash ──→（連写のまとめが出せる）
           └────→ display ──→（選別に出せる）
sidecar は scan の直後に 1 回読み、区切りごとに書く
```

- **`scan` が終わるまで選別は始められない。** 枚数と時間順が確定しないため
- `meta` が終われば時間順が確定し、**連写の基準学習は始められる**
- `hash` が終わればまとまりが確定する
- `display` は**追いつかなくても選別を始められる**。出来ていない写真は
  順番を後ろへ回す（§03）

---

## いつ書くか

### 原則

**「1 枚ごとに書く」でも「全部終わってから書く」でもなく、区切りで書く。**

| 作業 | 書く単位 | 理由 |
|---|---|---|
| `scan` | 200 枚ごと ＋ 最後 | 途中で止まっても数えた分は残る |
| `meta` `hash` `display` | 50 枚ごと ＋ 最後 ＋ **中断されたとき** | 1 枚ごとだと SQLite の書き込みが律速になる |
| 選別 | **グループを確定するたび** ＋ 選択が変わるたび | どこで止めても失わない |
| サイドカー | ラウンドの終わり／アプリが背面へ回るとき／明示の操作 | NAS への書き込みは高いので頻繁にやらない |

### 中断されたときは必ず書く

Android では背面へ回っただけで処理が止められる。**止まる前に書く。**
`cursor` に「どこまでやったか」を書き、次はそこから再開する。

いまはこれが無いため、**44/187 で止まったまま何も残っていなかった**。

## いつ消すか

**ここが今回いちばん壊れていた。**

### 成功したら、失敗の記録を必ず消す

```
1 枚の作業が成功した
  → photo_failures からその行を消す（kind を問わず、その kind の分だけ）
  → 「据え置きで済んだ」場合も消す
```

いまの実装は「据え置きで済んだら書く理由が無い」として**早期 return** しており、
**成功しても古いエラーが残り続けた**（実機で 172 枚）。

**「変わっていない」と「まだ失敗している」は別。**
据え置きでも「いま成功が確認できた」ことは書く。

### 作業が終わったら、作業の失敗も消す

```
jobs.state が done になった
  → jobs.failure を NULL にする
```

### 原本が差し替わったら、作ったものを捨てる

```
size か mtime が変わった
  → thumb_path / display_path / d_hash を NULL に
  → photo_failures のその写真の行も消す（前の原本の話なので）
```

## 警告を出す条件

**枚数ではなく「いま何が起きているか」で出す。**

| 出す条件 | 出す文 |
|---|---|
| `photo_failures` に行があり、かつ **その kind の job が `running` でない** | 「N 枚を読めませんでした」＋ 理由の内訳 ＋「もう一度試す」 |
| job が `failed` | 「◯◯が止まりました」＋ 理由 ＋「再開する」 |
| job が `paused`（背面へ回った等） | 出さない。戻ってきたら自動で再開する |
| job が `running` | 出さない。準備カードに `done / total` を出すだけ |

**「解析できませんでした」を、解析が走っている最中に出さない。**
いまは走っている最中でも古い件数が出るため、直ったのかどうかが分からない。

### 出さないもの

- 1 枚ごとの失敗を、その都度は出さない。**一覧のタイルに出す**（`photo_failures.reason`）
- 技術的な文言は「詳細」を開いたときだけ

---

## 選別に出す写真の選び方

`display` が追いつかないことは普通に起きる（NAS から 187 枚 × 6.7MB）。

```
次のグループを組むとき
  → 表示用が出来ている写真から先に組む
  → 足りなければ、出来ていない写真も入れる（サムネイルで代用し「準備中」と出す）
  → **順番は変わるが、止めない**
```

いまは出来ていない写真をそのまま出すため、**160×120 のサムネイルが
引き伸ばされて出る**（今回「著しく画質が悪い」と言われたもの）。

## 手で押したときの応答

**押したら必ず何かが変わる。**

| 操作 | 押した瞬間 | 進行中 | 終わったら |
|---|---|---|---|
| 「写真を再読み込み」 | `scan` を `running` に。準備カードが動く | `done / total` | 増減を 1 行「12 枚増えました」 |
| 「作り直す」 | 対象の `display_path` を NULL にし `display` を `running` に | 同上 | 「187 枚を作り直しました」 |
| 「もう一度試す」 | 失敗した写真だけを対象に該当の job を `running` に | 同上 | 残った失敗の件数 |

いまは「作り直す」を押しても**実際に何も動かず、画面も変わらない**。
押したことが `jobs` に残らないので、再開もされない。

---

## 起動時と再開時

```
アプリが起きた
  → jobs を読む
  → state が running のものは「前回落ちた」とみなし paused に倒す
  → プロジェクトを開いたら、そのプロジェクトの paused を running に戻す
     （cursor から再開）
```

**「開くたびに最初から解析し直す」ことはしない。**
いまは残作業を数え直して起動しているため、終わらない 15 枚のせいで
毎回走り続けていた。

### 背面へ回ったとき

```
onPause / visibilitychange
  → 走っている job を paused に。**その前に書き込む**
  → 前面に戻ったら running に戻す
```
